# 「今日」Tab 设计规范（v0.1 草案）

> 状态：草案 · 平台：Android 优先，iOS 后续按同一份文件格式对齐
> 原型：同目录 `index.html`（浏览器直接打开）

## 0. 背景与目标

Minis 现在的入口只有聊天，用户要"有事"才会打开。「今日」想让它变成一个**随手记录生活**的地方：写一句碎碎念、拍几张照片，按时间线自然排开。

**目标**

- 记录零门槛：不配置模型、不联网，也能完整使用
- 照片零操作：用相机拍的照片自动出现在当天的时间线上，同一时段的聚成一条
- 数据是用户自己的：纯文本 Markdown，人能读，agent 能读，挂到 Obsidian 里也能看

**第一版不做**

- 任何 AI 生成内容（照片说明、每日总结、自动打标签）
- iOS 版本
- 视频（Manifest 目前只声明了 `READ_MEDIA_IMAGES`，视频放到后续版本）
- 云同步之外的分享和导出

## 1. 信息架构

```
┌──────────────────────────┐
│  今日                     │  ← 新增：默认首页
│  聊天                     │  ← 现有的会话列表和聊天，原样放进来
└──────────────────────────┘
```

- 底部导航栏只有两个 tab：**今日**、**聊天**。纯文字、不带图标，选中的加粗并在下方显示一条短横线
- 只在两个 tab 的根页面显示底部栏；进入某个会话、设置、文件预览等二级页面时隐藏
- 冷启动默认进「今日」。深链接、快捷方式、通知点击仍然直达原来的目标页面，不受影响
- 设置入口留在「聊天」tab 原来的位置，「今日」右上角只放一个"⋯"菜单，里面是「今日」相关的设置

## 2. 「今日」页面

### 2.1 布局

```
┌─────────────────────────────┐
│ 今日            10月11日 周六 ⋯│  ← 顶栏
├─────────────────────────────┤
│        ── 昨天 · 10月10日 ── │  ← 日期分隔线
│ 19:05 │ [图][图][图][图]       │
│       │ 📍 南京西路            │
│ 21:40 │ 好累，早点睡           │
│        ── 今天 · 10月11日 ── │
│ 08:50 │ [  图  ]              │
│ 09:32 │ 今天的咖啡有点酸        │
│       │ 📍 静安寺附近          │
│   …   │                       │  ← 最新的在最下面
├─────────────────────────────┤
│ ╭ 写点什么…        📷 ╮ [↑]  │  ← 输入栏固定在底部，📷 在框内
├─────────────────────────────┤
│      [ 今日 ]   [ 聊天 ]      │
└─────────────────────────────┘
```

- **方向**：和聊天一样，最新的在最下面，打开时自动滚到底；往上滑是更早的内容，跨过日期分隔线就到了前一天
- **范围**：「今日」默认加载最近 7 天，往上滑到顶再按天加载更多。名字叫"今日"，是因为打开时看到的是今天
- **样式**：像日记本一样轻。每条上方一行浅灰小字写「时间 · 地点 · 已编辑」，下面直接是内容；碎碎念是纯文字，不加卡片；照片保持圆角。不用左侧时间轴、竖线和圆点，也**不用气泡**，避免和聊天 tab 混淆
- **空状态**：今天还没有记录时，在今天的分隔线下面显示一行浅色提示"今天还没有记录"

### 2.2 输入栏

- 一个圆角输入框，**相机按钮在框内右侧**，发送按钮在框外右侧
- 输入框最多长到 6 行，再多就在框内滚动
- 输入框为空且没有待发送的照片时，发送按钮置灰
- 软键盘弹出时整个输入栏跟着上移（`imePadding()`），时间线保持贴底
- **草稿**：切换 tab 或退出 App 都保留输入框内容，下次打开恢复

### 2.3 在「今日」里拍照

1. 点相机按钮，打开系统相机
2. 拍完回来，照片以缩略图的形式出现在**输入框内部、文字上方**，作为**待发送的照片**，可以点 × 移除（移除时同时从相册删掉这张，因为它是刚拍的）
3. 发送：
   - **有文字**：生成一条碎碎念，照片挂在这条下面显示
   - **没有文字**：不生成碎碎念，照片就是普通的相册照片，按 §5 的规则参与聚合
4. 照片在拍完的那一刻就已经写进系统相册了（§5.3）。"发送"只决定它是否挂在某条碎碎念下面

### 2.4 单条操作

长按任意一条，弹出底部菜单：

| 菜单项 | 碎碎念 | 照片组 |
|---|---|---|
| 问问 Minis | ✓ | ✓ |
| 编辑 | ✓ | — |
| 复制文字 | ✓ | — |
| 删除 | ✓（二次确认） | — |
| 在相册中打开 | — | ✓ |

- **问问 Minis**：切到「聊天」tab，新建一个会话，输入框里预先带上这条内容的引用卡片（文字原文，或者照片组的附件），光标停在输入框里，**不自动发送**
- **编辑**：在原位变成可编辑状态，保存后时间不变，元数据里记 `edited`
- 照片组**没有删除**：照片属于相册，要删就去相册删（§5.5）

### 2.5 查看照片

- 点哪张照片，就直接全屏打开哪张（点「+N」从第 4 张开始），左右滑动看同一条里的其他照片，不经过中间的网格页；只有一张时不显示「1 / 1」
- 照片组卡片**不显示"N 张"或时间范围**，只有缩略图，下面一行显示地名（有的话）。开始时间已经在左侧时间轴上
- 照片组卡片的缩略图排布：
  - 1 张：显示一张大图
  - 2–4 张：2×2 网格
  - 5 张及以上：显示前 3 张，第 4 格是"+N"

## 3. 时间线的数据来源

时间线上的每一条都来自两种数据之一：

| 类型 | 存在哪 | 怎么得到 |
|---|---|---|
| 碎碎念 | journal 文件（§4） | 解析文件 |
| 照片组 | **不存储** | 每次从系统相册查询，现场聚合（§5） |

照片组不写进文件，有三个好处：
- 不会出现文件里有、相册里已经删了的情况
- 聚合规则以后改了，历史数据自动按新规则显示
- journal 文件只包含用户亲手写的内容，干净

唯一的例外是 §2.3 里**挂在碎碎念下面的照片**。这种关联是用户的主动行为，需要记录，写在碎碎念的 `photos` 属性里。

## 4. journal 文件格式

### 4.1 位置

- Linux 路径：`/var/minis/journal/YYYY/MM/YYYY-MM-DD.md`
- 和 `memory`、`skills` 一样是全局目录，所有会话共享。Android 上实际存放在 `filesDir/minis-global/journal/`（和 `minis-global/memory/` 并列）
- 对 agent **只读**挂载，在「共享文件夹」设置里新增一项（`ui/settings/SharedFoldersScreen.kt`）
- 每个自然日一个文件。日期按**写下这条时的本地时区**计算

### 4.2 格式

```markdown
---
date: 2026-10-11
---

## 09:32
<!-- minis:entry id=01JA2K3M7ZQ8V5X4C3B2A1N0PR at=2026-10-11T09:32:15+08:00 lat=31.22345 lng=121.44567 acc=18 place="静安寺附近" -->
今天的咖啡有点酸。

## 14:05
<!-- minis:entry id=01JA2P9QK4M2N6B8V0C1X3Z5LT at=2026-10-11T14:05:02+08:00 edited=2026-10-11T14:07:40+08:00 -->
终于把 v1.14 发出去了。

## 这行是用户自己写的标题，不会被当成新的一条
正文可以是任意 Markdown。

## 16:20
<!-- minis:entry id=01JA2TB7W1E3R5T7Y9U1I3O5PA at=2026-10-11T16:20:44+08:00 photos="DCIM/Minis/MINIS_20261011_162031.jpg,DCIM/Minis/MINIS_20261011_162038.jpg" -->
楼下的猫又来了。
```

### 4.3 解析规则

- **front matter**：文件开头 `---` 包起来的部分，第一版只有 `date`。没有 front matter 也能正常解析，日期取文件名
- **一条记录的开始**：满足以下两个条件的位置
  1. 一行以 `## ` 开头
  2. **紧接着的下一行**以 `<!-- minis:entry ` 开头，以 ` -->` 结尾
- **记录正文**：元数据行之后，直到下一条记录开始或文件结束。去掉首尾的空行
- **`## HH:MM` 只是给人看的**，程序以 `at` 为准。两者不一致时（比如用户在 Obsidian 里改了标题）不报错，以 `at` 排序和显示
- **第一条记录之前的内容**（front matter 之外）：作为"前言"保留，不在时间线上显示，写文件时原样保留
- **无法解析的内容**一律原样保留，**任何情况下都不能因为解析失败丢掉用户写的字**

### 4.4 元数据属性

元数据写成 `key=value` 形式，用空格分隔。值里有空格、逗号或非 ASCII 字符时用双引号包起来。

| key | 必需 | 说明 |
|---|---|---|
| `id` | ✓ | ULID（26 位），按时间可排序，全局唯一 |
| `at` | ✓ | 创建时间，ISO 8601，**带时区偏移** |
| `edited` | | 最后编辑时间 |
| `lat` / `lng` | | WGS-84 坐标，保留 5 位小数（约 1 米） |
| `acc` | | 定位精度，单位米，取整 |
| `place` | | 反查到的地名，尽量获取，可以没有 |
| `photos` | | 挂在这条下面的照片，相册里的相对路径，用逗号分隔 |

- **转义**：双引号里的值，`"` 写成 `&quot;`，`&` 写成 `&amp;`，`--` 写成 `&#45;&#45;`（HTML 注释里不允许出现 `--`）
- **未知的 key**：解析时保留，写回时原样输出。这样新版本加的字段不会被旧版本删掉
- **正文里出现 `<!-- minis:entry`**：写入时转义成 `&lt;!-- minis:entry`，防止被误认成新的一条

### 4.5 写入规则

- **新增**：追加到文件末尾。文件不存在就先建目录和 front matter
- **编辑 / 删除 / 补充元数据**：按 `id` 找到这一条，**只替换这一条的文本范围**，文件其他部分一个字节都不动
- **原子写入**：先写临时文件，再 `rename` 覆盖原文件
- **外部修改**：用户可能在 Obsidian 或 shell 里改这个文件。写之前比较文件的修改时间和大小，变了就重新读一遍再操作；用 `FileObserver` 监听文件变化，变了就刷新时间线
- **id 冲突**（比如用户复制粘贴了整条）：都显示出来，但对重复的那条禁用编辑和删除，并在日志里报警告

### 4.6 和 memory 的区别

| | memory | journal |
|---|---|---|
| 谁写 | agent（`memory_write`） | 用户 |
| agent 权限 | 读写 | 只读 |
| 内容 | agent 对用户的理解 | 用户自己的原话 |
| 路径 | `/var/minis/memory/` | `/var/minis/journal/` |

agent 可以从 journal 里**提炼**内容写进 memory，但不能改 journal。

### 4.7 跨平台测试数据

参照 `src/shared/bashism/` 的做法，在 `src/shared/journal/` 下放解析测试数据（`journal_test_vectors.json`）：输入的 Markdown → 预期的解析结果 → 预期的写回结果。Android 和以后的 iOS 都用这一份数据做单元测试，保证两端读写同一个文件时结果一致。

## 5. 照片

### 5.1 怎么识别"拍的照片"

查询系统相册（`MediaStore.Images`），用路径判断：

```
取路径：
  Android 10 及以上（API 29+）：RELATIVE_PATH
  Android 8–9（API 26–28）：DATA 列，截取到 DCIM/ 或 Pictures/ 开头的部分

判断：
  以 DCIM/Minis/ 开头            → 是（来源：Minis）
  以 DCIM/Camera/ 开头（不分大小写）→ 是（来源：相机）
  在用户额外勾选的相册里           → 是
  其他                           → 否
```

- **第一版不用 EXIF 推测**。路径规则可以解释清楚，判断错了用户也能自己修正。EXIF 规则判断错了，用户会觉得莫名其妙
- **"包含的相册"设置**：在「今日」的 ⋯ 菜单里，列出相册里所有的相册（bucket），默认勾选自动识别出来的相机相册，用户可以多选。照顾相机目录不是 `DCIM/Camera` 的机型
- 截图、微信、下载等目录默认都不勾选

### 5.2 聚合规则

输入：某一天内所有被识别为"拍的照片"的列表，按拍摄时间 `DATE_TAKEN` 排序。`DATE_TAKEN` 为空时用 `DATE_ADDED`。

一张照片满足以下**任一条件**，就开始一个新组：

1. 和上一张的时间间隔 **超过 60 分钟**
2. 和上一张之间**有一条碎碎念**
3. 加入后整组的时间跨度会**超过 3 小时**
4. 和上一张**不在同一个自然日**

其他情况都归入上一张所在的组。

- 条件 2：「先拍几张、写一句、再拍几张」会显示成三条，和实际发生的顺序一致
- 条件 3：防止连续拍了一下午的照片被聚成一条
- 已经挂在碎碎念下面的照片（§2.3）不参与聚合
- 照片组在时间线上的位置按组里**第一张**的时间
- 聚合是纯函数（输入照片和碎碎念，输出时间线），单独写成一个类，配齐单元测试

### 5.3 在 Minis 里拍的照片写进相册

现在聊天里拍的照片写在 App 的私有目录里，**不会进入系统相册**。「今日」里拍的照片**最终写进相册**：

```
1. 先定好文件名 DCIM/Minis/MINIS_yyyyMMdd_HHmmss.jpg（同一秒内重名就加 _2、_3）
2. 让系统相机写到 App 私有的临时文件（FileProvider，和聊天拍照同一个 camera-photos/ 目录）
3. 回来以后检查临时文件大小（沿用 MIUI 的处理：不信 resultCode，只看文件）
     = 0：什么都不做
     > 0：Android 10 及以上 —— 插入 MediaStore 行（IS_PENDING=1）→ 复制 → IS_PENDING=0，
                               中途出错就删掉这一行
          Android 8–9       —— 复制到 DCIM/Minis/ 再通知相册扫描
4. 删除临时文件
```

> 为什么不直接把 MediaStore 的 URI 交给相机：`IS_PENDING=1` 的行只有拥有者能打开，
> 系统相机按"完成"时会写入失败（2026-10-11 在 API 35 模拟器上实测）；
> 去掉 IS_PENDING 又会让相册里短暂出现一张 0 字节的照片。

- 文件名由 Minis 决定，所以 `photos` 属性里存相对路径就是稳定的。不存 MediaStore 的 `_ID`，因为恢复备份或换手机以后 `_ID` 会变
- **聊天里的拍照不改**，还是存私有目录。以后可以加一个"聊天里拍的照片也存到相册"的开关
- 第一版用系统相机 Intent，和现有代码一致。以后可以换成 CameraX，在 App 里直接拍，不跳出去

### 5.4 去重

有的 ROM 的相机会忽略 `EXTRA_OUTPUT`，或者在写到指定位置的同时，在 `DCIM/Camera/` 里再存一份。

规则：一张 `DCIM/Camera/` 里的照片，如果和某张 `DCIM/Minis/` 里的照片**拍摄时间相差 3 秒以内**并且**宽高相同**，就当作重复的，不显示。

### 5.5 照片被删除或改动

- 用 `ContentObserver` 监听 `MediaStore.Images` 的变化，有变化就重新查询当天的照片并重新聚合（加 500ms 防抖）
- 照片组里的照片被删了：直接从组里消失，组空了这一条就消失
- 碎碎念 `photos` 里引用的照片找不到了：在原位置显示灰色占位"照片不在这台手机上"，**不改 journal 文件**
  - 不写"已删除"：App 分不清是用户删了，还是换手机后相册没恢复（§8.3），中性的说法不会吓到用户
  - 之后照片回来了（比如相册云服务恢复完成），引用会自动恢复显示

## 6. 位置

### 6.1 碎碎念的位置

**发送不等定位**：
1. 点发送，碎碎念立刻写进文件、显示在时间线上，位置一栏显示"定位中…"
2. 后台获取位置，复用 `sandbox/offload/LocationOffloadHandler.kt` 的策略：
   - 先遍历所有定位源的 `getLastKnownLocation`，**10 分钟以内**的结果直接用
   - 都没有就请求一次新的定位，**超时 15 秒**
3. 拿到坐标后，按 `id` 把 `lat`、`lng`、`acc` 补进这一条的元数据（§4.5 的局部替换）
4. 再用 `Geocoder` 反查地名，查到了补上 `place`。国内一些 ROM 没有 Google 服务，查不到就算了
5. 超时或没权限：去掉"定位中…"，不写任何位置属性，**不提示错误**

### 6.2 照片的位置

- 从照片 EXIF 里读 GPS
- **注意**：Android 10 起，相册返回的照片默认抹掉了 GPS。需要先获得 `ACCESS_MEDIA_LOCATION` 运行时权限（Manifest 已声明），再对 URI 调用 `MediaStore.setRequireOriginal(uri)` 打开原始文件，才能读到
- 照片组显示组内**第一张有 GPS 的照片**的地名
- 地名反查结果按坐标（取 3 位小数，约 100 米）缓存，避免重复请求

### 6.3 坐标系

- 存储一律用 WGS-84：系统定位和照片 EXIF 都是 WGS-84
- 第一版只显示地名，不显示地图。以后在国内显示地图时，再在显示层转成 GCJ-02，**不改存储**

### 6.4 开关

「今日」⋯ 菜单 → "记录位置"，默认开启。关掉以后新的碎碎念不再获取位置，照片组也不再显示地名。已经写进文件的位置不动。

## 7. 权限

**原则**：用到的时候才请求，并且先说明为什么要这个权限。被拒绝后功能降级，不反复弹窗。

| 权限 | 什么时候请求 | 被拒绝时 |
|---|---|---|
| `READ_MEDIA_IMAGES`（API 33+）/ `READ_EXTERNAL_STORAGE`（≤32） | 「今日」首次打开时，时间线顶部显示一张说明卡片，点"开启"才请求 | 不显示相册照片，卡片保留，可以再点 |
| `READ_MEDIA_VISUAL_USER_SELECTED`（API 34+，用户选择"部分照片"） | 同上 | 只显示用户选中的照片，顶部显示提示条"仅显示部分照片 · 管理" |
| `ACCESS_MEDIA_LOCATION` | 相册权限通过后，紧接着请求 | 照片组不显示地名 |
| `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION` | 第一次发送碎碎念并且"记录位置"开着时 | 关闭"记录位置"开关，提示一次"可以在 ⋯ 菜单里重新打开" |
| `CAMERA` | 第一次点相机按钮时（现有逻辑） | 现有逻辑 |

## 8. 备份

journal 是用户亲手写下的内容，丢了就找不回来，所以**从 M1 起就要能备份**。第一版只做备份，不做同步。

### 8.1 现有的备份机制（简述）

- 用户在设置里手动发起，把选中的类别打包成一个 `.minisbak` 文件，可以设密码加密
- Android 可以存到本地文件夹，或者通过 rclone 传到网盘；iOS 和 Android 的包格式通用
- 实现位置：Android `backup/`，iOS `Agent/Backup/`

### 8.2 新增 `journal` 类别

| 项目 | 规定 |
|---|---|
| 类别 key | `journal`。iOS 和 Android 必须用同一个字符串，否则备份包不能跨平台恢复 |
| 默认 | 备份时默认勾选 |
| 包内路径 | `data/journal/YYYY/MM/YYYY-MM-DD.md`，目录结构和源目录一致 |
| 统计数字 | 显示**碎碎念的条数**，不是文件数。用户看到"312 条"比"47 个文件"更好理解，也更容易发现少了东西（`exportMcpServers` 里统计服务器数而不是文件数，也是同样的考虑） |
| 加密 | 跟随整个备份包的加密设置，不单独处理 |
| 恢复顺序 | 排在 `memory` 之后 |

**和旧版本兼容**：两端读备份包时都会跳过不认识的类别（Android `BackupCategory.fromKey` 返回 null 后被过滤；iOS 的 manifest 把类别存成字符串字典）。所以：
- 新版本打的包，旧版本也能恢复，只是 journal 会被跳过
- iOS 在实现「今日」之前，至少要先能**恢复** `journal` 类别，否则用户从 Android 换到 iPhone 时会丢失 journal。这部分工作量很小，建议和 Android 的 M1 同期做

### 8.3 照片不在备份里

备份里只有 journal 文字和照片的**路径引用**，不包含照片本身。照片属于系统相册，由手机厂商的云服务或 Google 相册负责备份。

- 备份页面在 `journal` 类别下面加一行说明："照片由系统相册备份，不包含在这里"
- 换手机后如果相册也恢复了，`DCIM/Minis/` 下的文件名不变，引用自动对上
- 相册没恢复的照片显示"照片不在这台手机上"（§5.5）

### 8.4 恢复：按条合并，不覆盖文件

现有的 `memory` 恢复是**整个文件直接覆盖**（`BackupImporter.importMemory` 里的 `copyTo(overwrite = true)`）。journal **不能这样做**。比如在新手机上已经写了几条，再恢复旧备份，当天的文件一覆盖，新写的就没了。

journal 的恢复规则，按天逐个文件处理：

```
本地没有这一天的文件 → 直接复制过来
本地有：
  解析两边的文件，按 id 取并集
    只有一边有的条目      → 保留
    两边都有同一个 id     → 保留修改时间更晚的那份（edited，没有就用 at）
                          时间相同时保留本地的
  合并后按 at 排序，用 §4.5 的原子写入写回
  前言（第一条之前的内容）：保留本地的；本地没有就用备份里的
备份里的文件解析失败 → 原样存成 YYYY-MM-DD.restored-<恢复时间>.md 放在同一目录，
                     不合并、不丢弃，恢复报告里提示用户
```

- **删除不会被恢复**：备份之后在本地删掉的条目，恢复后会重新出现。恢复本来就是"把东西找回来"，宁可多不可少。恢复报告里写明"已合并 N 条，新增 M 条"
- 合并逻辑写成纯函数，测试数据放进 `src/shared/journal/`（§4.7），两端共用

### 8.5 以后再考虑

- **同步**：Android 目前没有同步功能，iOS 的 iCloud 同步也不覆盖 Android。等有多设备需求时，优先考虑让 journal 目录可以放进用户自己的同步文件夹（Syncthing、Obsidian 等），而不是自己实现
- **备份 Minis 拍的照片**：可以加一个可选的"包含 `DCIM/Minis/` 里的照片"，但会让备份包变大很多，见 §12

## 9. 和 agent 的关系（第一版范围）

第一版只做两件事：

1. **只读挂载** `/var/minis/journal/`，并在 system prompt 里加一行说明：
   > `/var/minis/journal/YYYY/MM/YYYY-MM-DD.md — The user's own journal (read-only). Each entry starts with "## HH:MM" followed by a "<!-- minis:entry ... -->" metadata line.`
2. **"问问 Minis"**（§2.4）

这样用户在聊天里问"我上周都干了什么"，agent 用现有的文件工具就能读 journal。查照片则用已有的 `android-photos` 能力。

## 13. 实现记录（Android，2026-10-11）

第一版在 `feat/today-tab` 分支实现了 M1–M4，和上文的差异与已知限制如下。

**和原设计的差异**

0. **底部 tab 不带图标**：只有文字；**时间线去掉左侧时间轴**，改为时间写在内容上方（2026-10-11 看过模拟器后决定）
1. **导航结构**：见 §10 的表格。「今日」是覆盖层，不是 NavHost 里的新路由，目的是不碰现有的启动、深链接和崩溃保护逻辑
2. **启动模式「自动」**：以前距离上次聊天超过 15 分钟会打开一个空白聊天草稿，现在改为停在「今日」；15 分钟内仍然恢复那个会话。「总是新聊天」「恢复上次会话」两种显式设置不变
3. **拍照流程**：见 §5.3，改为先写临时文件再复制进相册
4. **「今日」页的返回键**：把 App 退到后台（`moveTaskToBack`），不会弹出被盖住的聊天页面栈

**已知限制**

1. **shell 里的写入没有硬性拦截**：agent 的 `file_write` / `file_edit` 会拒绝写 `/var/minis/journal`，system prompt 也写明了只读；但 PRoot 不支持只读挂载，shell 里用 `>` 重定向仍然能写。目前靠 system prompt 约束
2. **FileObserver 不递归**：只监听当月和上月的目录。其他月份的外部修改，下次回到前台时会刷新
3. **地名依赖系统 Geocoder**：没有 Google 服务或断网时不显示地名，不报错（模拟器上两种情况都实测过）
4. **iOS 尚未支持 `journal` 备份类别**：iOS 恢复 Android 的备份时会跳过 journal（不会出错），需要按 §8.2 补上
