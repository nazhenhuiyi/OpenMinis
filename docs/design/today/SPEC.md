# 「今日」Tab 设计规范（v0.1 草案）

> 状态：草案 · 平台：Android 优先，iOS 后续按同一份文件格式对齐
> 原型：同目录 `index.html`（浏览器直接打开）

## 0. 背景与目标

Minis 现在的入口只有聊天，用户要"有事"才会打开。「今日」想让它变成一个**随手记录生活**的地方：写一句碎碎念、拍几张照片，按时间线自然排开。

**目标**

- 记录零门槛：不配置模型、不联网，也能完整使用
- 照片零操作：用相机拍的照片自动出现在当天的时间线上，同一时段的聚成一条
- 数据是用户自己的：纯文本 Markdown，人能读，agent 能读，挂到 Obsidian 里也能看

**第一版不做**

- 任何 AI 生成内容（照片说明、每日总结、自动打标签）
- iOS 版本
- ~~视频~~：2026-10-14 已加入时间线，见 §18
- 云同步之外的分享和导出

## 1. 信息架构

```
┌──────────────────────────┐
│  今日                     │  ← 新增：默认首页
│  聊天                     │  ← 现有的会话列表和聊天，原样放进来
└──────────────────────────┘
```

- 底部导航栏只有两个 tab：**今日**、**聊天**。纯文字、不带图标，选中的加粗并在下方显示一条短横线
- 只在两个 tab 的根页面显示底部栏；进入某个会话、设置、文件预览等二级页面时隐藏
- 冷启动默认进「今日」。深链接、快捷方式、通知点击仍然直达原来的目标页面，不受影响
- 设置入口留在「聊天」tab 原来的位置，「今日」右上角只放一个"⋯"菜单。2026-10-16 起（作者：配置太多）菜单里只剩「每日打卡」和「设置」；记录位置、天气、天气提醒、包含的相册、心情颜色、智能建议、物种识别用 CPU 都在一个单独的设置页里，探索页右上角的齿轮也能打开。下文说的「⋯ 菜单里的某开关」都指这个设置页

## 2. 「今日」页面

### 2.1 布局

```
┌─────────────────────────────┐
│ 今日            10月11日 周六 ⋯│  ← 顶栏
├─────────────────────────────┤
│        ── 昨天 · 10月10日 ── │  ← 日期分隔线
│ 19:05 │ [图][图][图][图]       │
│       │ 📍 南京西路            │
│ 21:40 │ 好累，早点睡           │
│        ── 今天 · 10月11日 ── │
│ 08:50 │ [  图  ]              │
│ 09:32 │ 今天的咖啡有点酸        │
│       │ 📍 静安寺附近          │
│   …   │                       │  ← 最新的在最下面
├─────────────────────────────┤
│ ╭ 写点什么…        📷 ╮ [↑]  │  ← 输入栏固定在底部，📷 在框内
├─────────────────────────────┤
│      [ 今日 ]   [ 聊天 ]      │
└─────────────────────────────┘
```

- **方向**：和聊天一样，最新的在最下面，打开时自动滚到底；往上滑是更早的内容，跨过日期分隔线就到了前一天
- **范围**：「今日」默认加载最近 7 天，往上滑到顶再按天加载更多。名字叫"今日"，是因为打开时看到的是今天
- **样式**：像日记本一样轻。每条上方一行浅灰小字写「时间 · 地点 · 已编辑」，下面直接是内容；碎碎念是纯文字，不加卡片；照片保持圆角。不用左侧时间轴、竖线和圆点，也**不用气泡**，避免和聊天 tab 混淆
- **空状态**：今天还没有记录时，在今天的分隔线下面显示一行浅色提示"今天还没有记录"

### 2.2 输入栏

- 和聊天输入框同一套样式：一张圆角卡片，**文字在上，按钮行在卡片内的底部**——左下角是相机，右下角是发送
- 为写长一点的内容设计：最多长到 10 行，再多就在框内滚动；回车是换行，只有点发送才会发送
- 输入框为空且没有待发送的照片时，发送按钮置灰
- 软键盘弹出时整个输入栏跟着上移（`imePadding()`），时间线保持贴底
- **草稿**：切换 tab 或退出 App 都保留输入框内容，下次打开恢复

### 2.3 在「今日」里拍照

1. 点相机按钮，打开系统相机
2. 拍完回来，照片以缩略图的形式出现在**输入框内部、文字上方**，作为**待发送的照片**，可以点 × 移除（移除时同时从相册删掉这张，因为它是刚拍的）
3. 发送：
   - **有文字**：生成一条碎碎念，照片挂在这条下面显示
   - **没有文字**：不生成碎碎念，照片就是普通的相册照片，按 §5 的规则参与聚合
4. 照片在拍完的那一刻就已经写进系统相册了（§5.3）。"发送"只决定它是否挂在某条碎碎念下面

### 2.4 单条操作

长按任意一条，弹出底部菜单：

| 菜单项 | 碎碎念 | 照片组 |
|---|---|---|
| 问问 Minis | ✓ | ✓ |
| 编辑 | ✓ | — |
| 复制文字 | ✓ | — |
| 删除 | ✓（二次确认） | — |
| 在相册中打开 | — | ✓ |

- **问问 Minis**：切到「聊天」tab，新建一个会话，输入框里预先带上这条内容的引用卡片（文字原文，或者照片组的附件），光标停在输入框里，**不自动发送**
- **编辑**：在原位变成可编辑状态，保存后时间不变，元数据里记 `edited`
- 照片组**没有删除**：照片属于相册，要删就去相册删（§5.5）

### 2.5 查看照片

- 点哪张照片，就直接全屏打开哪张（点「+N」从第 4 张开始），左右滑动看同一条里的其他照片，不经过中间的网格页；只有一张时不显示「1 / 1」
- 照片组卡片**不显示"N 张"或时间范围**，只有缩略图，下面一行显示地名（有的话）。开始时间已经在左侧时间轴上
- 照片组卡片的缩略图排布：
  - 1 张：显示一张大图
  - 2–4 张：2×2 网格
  - 5 张及以上：显示前 3 张，第 4 格是"+N"

## 3. 时间线的数据来源

时间线上的每一条都来自两种数据之一：

| 类型 | 存在哪 | 怎么得到 |
|---|---|---|
| 碎碎念 | journal 文件（§4） | 解析文件 |
| 照片组 | **不存储** | 每次从系统相册查询，现场聚合（§5） |

照片组不写进文件，有三个好处：
- 不会出现文件里有、相册里已经删了的情况
- 聚合规则以后改了，历史数据自动按新规则显示
- journal 文件只包含用户亲手写的内容，干净

唯一的例外是 §2.3 里**挂在碎碎念下面的照片**。这种关联是用户的主动行为，需要记录，写在碎碎念的 `photos` 属性里。

## 4. journal 文件格式

### 4.1 位置

- Linux 路径：`/var/minis/journal/YYYY/MM/YYYY-MM-DD.md`
- 和 `memory`、`skills` 一样是全局目录，所有会话共享。Android 上实际存放在 `filesDir/minis-global/journal/`（和 `minis-global/memory/` 并列）
- 挂载给 agent：文件本身只读（`file_write` / `file_edit` 会拒绝），增删改一律通过 `journal` 工具（§9）；在「共享文件夹」设置里新增一项（`ui/settings/SharedFoldersScreen.kt`）
- 每个自然日一个文件。日期按**写下这条时的本地时区**计算

### 4.2 格式

```markdown
---
date: 2026-10-11
---

## 09:32
<!-- minis:entry id=01JA2K3M7ZQ8V5X4C3B2A1N0PR at=2026-10-11T09:32:15+08:00 lat=31.22345 lng=121.44567 acc=18 place="静安寺附近" -->
今天的咖啡有点酸。

## 14:05
<!-- minis:entry id=01JA2P9QK4M2N6B8V0C1X3Z5LT at=2026-10-11T14:05:02+08:00 edited=2026-10-11T14:07:40+08:00 -->
终于把 v1.14 发出去了。

## 这行是用户自己写的标题，不会被当成新的一条
正文可以是任意 Markdown。

## 16:20
<!-- minis:entry id=01JA2TB7W1E3R5T7Y9U1I3O5PA at=2026-10-11T16:20:44+08:00 photos="DCIM/Minis/MINIS_20261011_162031.jpg,DCIM/Minis/MINIS_20261011_162038.jpg" -->
楼下的猫又来了。
```

### 4.3 解析规则

- **front matter**：文件开头 `---` 包起来的部分，第一版只有 `date`。没有 front matter 也能正常解析，日期取文件名
- **一条记录的开始**：满足以下两个条件的位置
  1. 一行以 `## ` 开头
  2. **紧接着的下一行**以 `<!-- minis:entry ` 开头，以 ` -->` 结尾
- **记录正文**：元数据行之后，直到下一条记录开始或文件结束。去掉首尾的空行
- **`## HH:MM` 只是给人看的**，程序以 `at` 为准。两者不一致时（比如用户在 Obsidian 里改了标题）不报错，以 `at` 排序和显示
- **第一条记录之前的内容**（front matter 之外）：作为"前言"保留，不在时间线上显示，写文件时原样保留
- **无法解析的内容**一律原样保留，**任何情况下都不能因为解析失败丢掉用户写的字**

### 4.4 元数据属性

元数据写成 `key=value` 形式，用空格分隔。值里有空格、逗号或非 ASCII 字符时用双引号包起来。

| key | 必需 | 说明 |
|---|---|---|
| `id` | ✓ | ULID（26 位），按时间可排序，全局唯一 |
| `at` | ✓ | 创建时间，ISO 8601，**带时区偏移** |
| `edited` | | 最后编辑时间 |
| `lat` / `lng` | | WGS-84 坐标，保留 5 位小数（约 1 米） |
| `acc` | | 定位精度，单位米，取整 |
| `place` | | 反查到的地名，尽量获取，可以没有 |
| `photos` | | 挂在这条下面的照片，相册里的相对路径，用逗号分隔 |

- **转义**：双引号里的值，`"` 写成 `&quot;`，`&` 写成 `&amp;`，`--` 写成 `&#45;&#45;`（HTML 注释里不允许出现 `--`）
- **未知的 key**：解析时保留，写回时原样输出。这样新版本加的字段不会被旧版本删掉
- **正文里出现 `<!-- minis:entry`**：写入时转义成 `&lt;!-- minis:entry`，防止被误认成新的一条

### 4.5 写入规则

- **新增**：追加到文件末尾。文件不存在就先建目录和 front matter
- **编辑 / 删除 / 补充元数据**：按 `id` 找到这一条，**只替换这一条的文本范围**，文件其他部分一个字节都不动
- **原子写入**：先写临时文件，再 `rename` 覆盖原文件
- **外部修改**：用户可能在 Obsidian 或 shell 里改这个文件。写之前比较文件的修改时间和大小，变了就重新读一遍再操作；用 `FileObserver` 监听文件变化，变了就刷新时间线
- **id 冲突**（比如用户复制粘贴了整条）：都显示出来，但对重复的那条禁用编辑和删除，并在日志里报警告

### 4.6 和 memory 的区别

| | memory | journal |
|---|---|---|
| 谁写 | agent（`memory_write`） | 主要是用户；用户让 agent 记的时候 agent 也能写 |
| agent 权限 | 读写 | 读；写只能通过 `journal` 工具，并且只在用户要求时 |
| 内容 | agent 对用户的理解 | 用户的生活记录 |
| 路径 | `/var/minis/memory/` | `/var/minis/journal/` |

**署名**：agent 新增或改过的条目带 `by=minis` 属性，时间线上那一行小字显示「Minis 写的」。用户之后在 App 里再改这一条，`by` 会被去掉——文字又是用户自己的了。

### 4.7 跨平台测试数据

参照 `src/shared/bashism/` 的做法，在 `src/shared/journal/` 下放解析测试数据（`journal_test_vectors.json`）：输入的 Markdown → 预期的解析结果 → 预期的写回结果。Android 和以后的 iOS 都用这一份数据做单元测试，保证两端读写同一个文件时结果一致。

## 5. 照片

### 5.1 怎么识别"拍的照片"

查询系统相册（`MediaStore.Images`），用路径判断：

```
取路径：
  Android 10 及以上（API 29+）：RELATIVE_PATH
  Android 8–9（API 26–28）：DATA 列，截取到 DCIM/ 或 Pictures/ 开头的部分

判断：
  以 DCIM/Minis/ 开头            → 是（来源：Minis）
  以 DCIM/Camera/ 开头（不分大小写）→ 是（来源：相机）
  在用户额外勾选的相册里           → 是
  其他                           → 否
```

- **第一版不用 EXIF 推测**。路径规则可以解释清楚，判断错了用户也能自己修正。EXIF 规则判断错了，用户会觉得莫名其妙
- **"包含的相册"设置**：在「今日」的 ⋯ 菜单里，列出相册里所有的相册（bucket），默认勾选自动识别出来的相机相册，用户可以多选。照顾相机目录不是 `DCIM/Camera` 的机型
- 截图、微信、下载等目录默认都不勾选

### 5.2 聚合规则

输入：某一天内所有被识别为"拍的照片"的列表，按拍摄时间 `DATE_TAKEN` 排序。`DATE_TAKEN` 为空时用 `DATE_ADDED`。

一张照片满足以下**任一条件**，就开始一个新组：

1. 和上一张的时间间隔 **超过 60 分钟**
2. 和上一张之间**有一条碎碎念**
3. 加入后整组的时间跨度会**超过 3 小时**
4. 和上一张**不在同一个自然日**

其他情况都归入上一张所在的组。

- 条件 2：「先拍几张、写一句、再拍几张」会显示成三条，和实际发生的顺序一致
- 条件 3：防止连续拍了一下午的照片被聚成一条
- 已经挂在碎碎念下面的照片（§2.3）不参与聚合
- 照片组在时间线上的位置按组里**第一张**的时间
- 聚合是纯函数（输入照片和碎碎念，输出时间线），单独写成一个类，配齐单元测试

### 5.3 在 Minis 里拍的照片写进相册

现在聊天里拍的照片写在 App 的私有目录里，**不会进入系统相册**。「今日」里拍的照片**最终写进相册**：

```
1. 先定好文件名 DCIM/Minis/MINIS_yyyyMMdd_HHmmss.jpg（同一秒内重名就加 _2、_3）
2. 让系统相机写到 App 私有的临时文件（FileProvider，和聊天拍照同一个 camera-photos/ 目录）
3. 回来以后检查临时文件大小（沿用 MIUI 的处理：不信 resultCode，只看文件）
     = 0：什么都不做
     > 0：Android 10 及以上 —— 插入 MediaStore 行（IS_PENDING=1）→ 复制 → IS_PENDING=0，
                               中途出错就删掉这一行
          Android 8–9       —— 复制到 DCIM/Minis/ 再通知相册扫描
4. 删除临时文件
```

> 为什么不直接把 MediaStore 的 URI 交给相机：`IS_PENDING=1` 的行只有拥有者能打开，
> 系统相机按"完成"时会写入失败（2026-10-11 在 API 35 模拟器上实测）；
> 去掉 IS_PENDING 又会让相册里短暂出现一张 0 字节的照片。

- 文件名由 Minis 决定，所以 `photos` 属性里存相对路径就是稳定的。不存 MediaStore 的 `_ID`，因为恢复备份或换手机以后 `_ID` 会变
- **聊天里的拍照不改**，还是存私有目录。以后可以加一个"聊天里拍的照片也存到相册"的开关
- 第一版用系统相机 Intent，和现有代码一致。以后可以换成 CameraX，在 App 里直接拍，不跳出去

### 5.4 去重

有的 ROM 的相机会忽略 `EXTRA_OUTPUT`，或者在写到指定位置的同时，在 `DCIM/Camera/` 里再存一份。

规则：一张 `DCIM/Camera/` 里的照片，如果和某张 `DCIM/Minis/` 里的照片**拍摄时间相差 3 秒以内**并且**宽高相同**，就当作重复的，不显示。

### 5.5 照片被删除或改动

- 用 `ContentObserver` 监听 `MediaStore.Images` 的变化，有变化就重新查询当天的照片并重新聚合（加 500ms 防抖）
- 照片组里的照片被删了：直接从组里消失，组空了这一条就消失
- 碎碎念 `photos` 里引用的照片找不到了：在原位置显示灰色占位"照片不在这台手机上"，**不改 journal 文件**
  - 不写"已删除"：App 分不清是用户删了，还是换手机后相册没恢复（§8.3），中性的说法不会吓到用户
  - 之后照片回来了（比如相册云服务恢复完成），引用会自动恢复显示

## 6. 位置

### 6.1 碎碎念的位置

**发送不等定位**：
1. 点发送，碎碎念立刻写进文件、显示在时间线上，位置一栏显示"定位中…"
2. 后台获取位置，复用 `sandbox/offload/LocationOffloadHandler.kt` 的策略：
   - 先遍历所有定位源的 `getLastKnownLocation`，**10 分钟以内**的结果直接用
   - 都没有就请求一次新的定位，**超时 15 秒**
3. 拿到坐标后，按 `id` 把 `lat`、`lng`、`acc` 补进这一条的元数据（§4.5 的局部替换）
4. 再用 `Geocoder` 反查地名，查到了补上 `place`。国内一些 ROM 没有 Google 服务，查不到就算了
5. 超时或没权限：去掉"定位中…"，不写任何位置属性，**不提示错误**

### 6.2 照片的位置

- 从照片 EXIF 里读 GPS
- **注意**：Android 10 起，相册返回的照片默认抹掉了 GPS。需要先获得 `ACCESS_MEDIA_LOCATION` 运行时权限（Manifest 已声明），再对 URI 调用 `MediaStore.setRequireOriginal(uri)` 打开原始文件，才能读到
- 照片组显示组内**第一张有 GPS 的照片**的地名
- 地名反查结果按坐标（取 3 位小数，约 100 米）缓存，避免重复请求

### 6.3 坐标系

- 存储一律用 WGS-84：系统定位和照片 EXIF 都是 WGS-84
- 第一版只显示地名，不显示地图。以后在国内显示地图时，再在显示层转成 GCJ-02，**不改存储**

### 6.4 开关

「今日」⋯ 菜单 → "记录位置"，默认开启。关掉以后新的碎碎念不再获取位置，照片组也不再显示地名。已经写进文件的位置不动。

## 7. 权限

**原则**：用到的时候才请求，并且先说明为什么要这个权限。被拒绝后功能降级，不反复弹窗。

| 权限 | 什么时候请求 | 被拒绝时 |
|---|---|---|
| `READ_MEDIA_IMAGES`（API 33+）/ `READ_EXTERNAL_STORAGE`（≤32） | 「今日」首次打开时，时间线顶部显示一张说明卡片，点"开启"才请求 | 不显示相册照片，卡片保留，可以再点 |
| `READ_MEDIA_VISUAL_USER_SELECTED`（API 34+，用户选择"部分照片"） | 同上 | 只显示用户选中的照片，顶部显示提示条"仅显示部分照片 · 管理" |
| `ACCESS_MEDIA_LOCATION` | 相册权限通过后，紧接着请求 | 照片组不显示地名 |
| `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION` | 第一次发送碎碎念并且"记录位置"开着时 | 关闭"记录位置"开关，提示一次"可以在 ⋯ 菜单里重新打开" |
| `CAMERA` | 第一次点相机按钮时（现有逻辑） | 现有逻辑 |

## 8. 备份

journal 是用户亲手写下的内容，丢了就找不回来，所以**从 M1 起就要能备份**。第一版只做备份，不做同步。

### 8.1 现有的备份机制（简述）

- 用户在设置里手动发起，把选中的类别打包成一个 `.minisbak` 文件，可以设密码加密
- Android 可以存到本地文件夹，或者通过 rclone 传到网盘；iOS 和 Android 的包格式通用
- 实现位置：Android `backup/`，iOS `Agent/Backup/`

### 8.2 新增 `journal` 类别

| 项目 | 规定 |
|---|---|
| 类别 key | `journal`。iOS 和 Android 必须用同一个字符串，否则备份包不能跨平台恢复 |
| 默认 | 备份时默认勾选 |
| 包内路径 | `data/journal/YYYY/MM/YYYY-MM-DD.md`，目录结构和源目录一致 |
| 统计数字 | 显示**碎碎念的条数**，不是文件数。用户看到"312 条"比"47 个文件"更好理解，也更容易发现少了东西（`exportMcpServers` 里统计服务器数而不是文件数，也是同样的考虑） |
| 加密 | 跟随整个备份包的加密设置，不单独处理 |
| 恢复顺序 | 排在 `memory` 之后 |

**和旧版本兼容**：两端读备份包时都会跳过不认识的类别（Android `BackupCategory.fromKey` 返回 null 后被过滤；iOS 的 manifest 把类别存成字符串字典）。所以：
- 新版本打的包，旧版本也能恢复，只是 journal 会被跳过
- iOS 在实现「今日」之前，至少要先能**恢复** `journal` 类别，否则用户从 Android 换到 iPhone 时会丢失 journal。这部分工作量很小，建议和 Android 的 M1 同期做

### 8.3 照片不在备份里

备份里只有 journal 文字和照片的**路径引用**，不包含照片本身。照片属于系统相册，由手机厂商的云服务或 Google 相册负责备份。

- 备份页面在 `journal` 类别下面加一行说明："照片由系统相册备份，不包含在这里"
- 换手机后如果相册也恢复了，`DCIM/Minis/` 下的文件名不变，引用自动对上
- 相册没恢复的照片显示"照片不在这台手机上"（§5.5）

### 8.4 恢复：按条合并，不覆盖文件

现有的 `memory` 恢复是**整个文件直接覆盖**（`BackupImporter.importMemory` 里的 `copyTo(overwrite = true)`）。journal **不能这样做**。比如在新手机上已经写了几条，再恢复旧备份，当天的文件一覆盖，新写的就没了。

journal 的恢复规则，按天逐个文件处理：

```
本地没有这一天的文件 → 直接复制过来
本地有：
  解析两边的文件，按 id 取并集
    只有一边有的条目      → 保留
    两边都有同一个 id     → 保留修改时间更晚的那份（edited，没有就用 at）
                          时间相同时保留本地的
  合并后按 at 排序，用 §4.5 的原子写入写回
  前言（第一条之前的内容）：保留本地的；本地没有就用备份里的
备份里的文件解析失败 → 原样存成 YYYY-MM-DD.restored-<恢复时间>.md 放在同一目录，
                     不合并、不丢弃，恢复报告里提示用户
```

- **删除不会被恢复**：备份之后在本地删掉的条目，恢复后会重新出现。恢复本来就是"把东西找回来"，宁可多不可少。恢复报告里写明"已合并 N 条，新增 M 条"
- 合并逻辑写成纯函数，测试数据放进 `src/shared/journal/`（§4.7），两端共用

### 8.5 以后再考虑

- **同步**：Android 目前没有同步功能，iOS 的 iCloud 同步也不覆盖 Android。等有多设备需求时，优先考虑让 journal 目录可以放进用户自己的同步文件夹（Syncthing、Obsidian 等），而不是自己实现
- **备份 Minis 拍的照片**：可以加一个可选的"包含 `DCIM/Minis/` 里的照片"，但会让备份包变大很多，见 §12

## 9. 和 agent 的关系（第一版范围）

1. **挂载** `/var/minis/journal/`，system prompt 里说明位置、格式，以及"改动请用 `journal` 工具"
2. **`journal` 工具**（`tools/JournalTool.kt`），只给主 agent，子 agent 只能读文件：

   | action | 参数 | 说明 |
   |---|---|---|
   | `list` | `date`（默认今天） | 返回当天每条的 id、时间、地点、照片、是否 Minis 写的、正文 |
   | `add` | `content`，可选 `date` + `time`、`photos` | 新增一条，标 `by=minis`；不给 `time` 就是"现在"（只限今天），补记别的日子必须给 `time`（"把昨晚看电影记一下"），不能写未来。当天已有一条 Minis 写的、正文完全相同的，不再新建，返回那条的 id。记"现在"的条目和 App 里发的一样，开着"记录位置"时在后台补上位置 |
   | `edit` | `id`，加 `content` / `date` / `time` / `photos` 至少一个 | 按 id 在所有日期里找到；改正文时标 `by=minis`；改时间会挪到对应那天的文件，只挪不改字，不标 `by`；`photos` 追加到已有照片；都补 `edited` |
   | `delete` | `id` | 删除这一条，照片留在相册 |

   `photos` 是逗号分隔的沙箱路径（如聊天附件 `/var/minis/attachments/uploads/…`）。相册里已经有字节完全相同的照片（从相册选的图、「问问 Minis」带过去的图）就直接引用原图；没有的（聊天里现拍的、下载的）复制进相册 `DCIM/Minis/`，拍摄时间取 EXIF。路径找不到时整次调用失败，什么都不写。

   每次的返回结果末尾都带当前本地时间：system prompt 为了缓存只写日期，模型不知道几点，会把附件的时间戳当成现在（2026-10-13 记成了 00:40）。子 agent 没有这个工具，prompt 里也告诉它 journal 只读。

   读写都走 `JournalStore`，所以 id、时间戳和元数据行一定是对的。工具说明里要求：只在用户要求或明确同意时写，保留用户的语气，不主动改写或删除用户的原话。
3. **"问问 Minis"**（§2.4）：引用里带完整日期和条目 id（"我在 2026-10-12 13:37 写的碎碎念（已在「今日」里，id=…）"），模型不用先 `list` 去找，也不会把旧的一条当成没记过

这样用户在聊天里问"我上周都干了什么"，agent 读 journal 就能回答；说"帮我把今天的事记一下"，agent 用 `journal add` 写进去。查照片则用已有的 `android-photos` 能力。

## 14. 每日打卡（2026-10-12 新增）

像 todo list 一样的日常打卡：用户自己定义每天要做的事（"20 个俯卧撑""50 个深蹲""冥想"），在「今日」里一点就记下来。

### 14.1 已定的规则

- **打卡项完全由用户自定义**：名称、目标数量和单位（可选，不填就是简单的勾选）、哪几天要打卡（默认每天）
- **只能打今天的卡，不能补**：App 里只有今天的卡片能点；agent 的 `journal` 工具也只能给今天打卡。过去的打卡记录只读
- **可以分组累加**：深蹲上午 30 个、下午 20 个，记在同一条记录里，`done` 累加到 50
- **数据放在 journal 里**：打卡项定义是一个单独的文件，打卡记录是当天 journal 文件里的普通条目（§14.2）。所以备份、Obsidian、agent 读取都直接沿用现有机制

### 14.2 文件格式

**打卡项定义**：`/var/minis/journal/habits.md`，一行一项，顺序就是显示顺序：

```markdown
---
type: habits
---

- 俯卧撑 <!-- minis:habit id=01JA3B... target=20 unit="个" -->
- 深蹲 <!-- minis:habit id=01JA3C... target=50 unit="个" days="mon,tue,wed,thu,fri" -->
- 冥想 <!-- minis:habit id=01JA3D... -->
- 跑步 <!-- minis:habit id=01JA3E... target=5 unit=km archived=2026-10-12 -->
```

| key | 必需 | 说明 |
|---|---|---|
| `id` | ✓ | ULID，打卡记录靠它关联，改名不影响历史 |
| `target` | | 每天的目标数量，正整数。没有就是勾选型 |
| `unit` | | 单位，只用于显示 |
| `days` | | 哪几天要打卡：`mon,tue,…,sun` 的子集。没有 = 每天 |
| `archived` | | 删除的日期。删除只是归档，不真的删掉这一行，历史记录里还能显示名字 |

- 名称是 `- ` 和注释之间的文字，去掉首尾空格；只能一行
- 不符合格式的行原样保留；改动只替换目标那一行（和 §4.5 一样）
- 文件名不是日期，所以不会被当成某一天的 journal

**打卡记录**：当天 journal 文件里的一条普通条目，多两个属性：

```markdown
## 07:45
<!-- minis:entry id=01JA3F... at=2026-10-12T07:45:10+08:00 habit=01JA3C... done=30 edited=2026-10-12T18:20:02+08:00 -->
深蹲 30/50 个
```

- `habit`：打卡项的 id；`done`：今天累计完成的数量（勾选型固定为 1）
- `at` 是当天第一次打卡的时间；之后累加只改 `done` 和正文，并补 `edited`（恢复备份时按 §8.4 比较新旧）
- 正文是给人看的（"深蹲 30/50 个"，完成了前面加 ✅），程序只认属性
- **同一天同一项有多条**（比如在 Obsidian 里手写了一条，或者两台手机的备份合并后）：显示时 `done` 相加；App 再打卡时改最后一条
- 有 `habit` 属性的条目不当作碎碎念，而是**汇总到当天开头的打卡块**里（§14.3）

- **「每日打卡」页**：一个全屏页面，打卡和管理都在这里，不用弹框（2026-10-15 用户反馈：原来是底部面板 + 单独的管理弹框，合成一页）。入口：顶栏进度圈、「⋯」菜单 →「每日打卡」、时间线里的打卡块、晚间提醒通知（§14.6）

### 14.4 和 agent

`journal` 工具新增这些 action：

| action | 参数 | 说明 |
|---|---|---|
| `habits` | | 列出打卡项（id、名称、目标、哪几天）和今天每项的进度 |
| `check_in` | `habit`（id 或名称），可选 `count` | 给**今天**打卡。`count` 是这次增加的数量，可以为负（"其实只做了 15 个"）；不填 = 补满到目标。累计到 0 就删掉这条 |
| `add_habit` | `name`，可选 `target` `unit` `days` | 新增打卡项，追加到末尾。`days` 是 `mon,wed,fri` 这样的列表，不填 = 每天。已有同名（未归档）的项就不加，返回那一项 |
| `edit_habit` | `habit`，以及 `name` `target` `unit` `days` 中至少一个 | 只改给出的字段。`target=0` 改成勾选型，`days=daily` 改回每天。不能改成和别的项同名 |
| `remove_habit` | `habit` | 归档，和 App 里的删除一样（§14.2） |

- 不能给过去的日期打卡（§14.1）
- 打卡项是用户自己的计划：agent 只在用户要求、或明确同意一份具体清单时才增删改，不会自己"优化"。最早不让 agent 改打卡项，用户在聊天里让它按建议改清单时它做不到，于是放开（2026-10-14）
- `edit` 不能改打卡记录（会让正文和 `done` 对不上），提示改用 `check_in`；`delete` 可以

### 14.6 晚间提醒（2026-10-15 新增）

每天晚上最多一条通知，**只在今天还有没打完的项时才发**：

```
今日打卡还差 2 项
俄罗斯转体 2/5 组 · 蛋白粉
```

- **时间**：默认 20:00，在「每日打卡」页底部的「晚间提醒」里改时间或关掉；系统设置里也有单独的「打卡提醒」通知类别
- **通知被系统关掉时**（整个 App 的通知、或者「打卡提醒」这个类别），提醒那一行下面用红字写「通知被关掉了，提醒发不出来　去开启」，点了跳到对应的系统设置；从设置回来自动重新检查。不然提醒一直不来，看起来像功能坏了
- **只列今天要打卡、还没完成的项**（按 `days` 过滤，不含已归档的），按 `habits.md` 的顺序；做了一部分的写上进度
- 全部完成、或者今天没有要打卡的项：不发
- **一天只检查一次**：到点检查，不管发没发，当天都不再检查；没完成也不再催，不提"断了几天"
- 手机在提醒时间关机或者闹钟被系统丢掉，2 小时内回来还会补发，再晚就算了
- **通知会跟着更新**：通知还在时打了卡（App 里、agent、Obsidian、通知自己的按钮），列表里去掉完成的项，全部完成就自动收起。App 启动时就开始监听 journal 的写入，不依赖今日页开着；没有通知挂着时什么都不做
- **点通知**打开「每日打卡」页（深链接 `minis://today/habits`，冷启动时不会先跳到上次的聊天）；**只剩一项**时通知上有「补满」（勾选型是「完成」）按钮，直接记完
- 用系统闹钟定时（不精确的那种，晚几分钟没关系，不需要精确闹钟权限），每次触发后定好下一次；开机、App 更新后重新定。文案是固定模板，不用模型，离线也能发
- 不用日历事件或时钟 App 的闹钟：它们到点就响，不知道你做没做完，也不能点开就打卡（2026-10-15 讨论）

## 15. 天气（2026-10-12 新增）

在每天的日期分隔线里写上这一天的天气，像日记本的页眉：

```
──── 今天 · 10月12日周一 · 🌦 小雨 18–23° ────
──── 昨天 · 10月11日周日 · ☀️ 晴 16–24° ────
```

### 15.1 已定的规则

- **放在分隔线里**，不单独做天气卡片：「今日」是日记，不是天气 App
- **记下来，不现查**：天气写进当天 journal 文件的 front matter。过去的天显示当时记下的天气，不联网也能看；Obsidian 和 agent 都能读到
- **只显示一天的概况**：图标 + 一个词 + 最低到最高温。不显示实时温度、湿度、风力
- **默认开启**，「⋯」菜单里「显示天气」可以关。关掉后不再获取，也不显示；已经记下的天气留在文件里不删

### 15.2 文件格式

```markdown
---
date: 2026-10-12
weather: 🌧 小雨 18–23°
weather_code: 61
temp_min: 18
temp_max: 23
weather_updated: "2026-10-12T08:00:00+08:00"
---
```

- `weather` 是给人看的一行，用写入时的界面语言；程序只读 `weather_code`（WMO 天气代码）、`temp_min`、`temp_max`，显示时按当前语言重新翻译
- front matter 里其他的行（包括用户自己加的）原样保留；改天气只替换这几个 key，正文一个字节都不动
- 当天还没有文件时，只写 front matter 也会建文件；之后的碎碎念和打卡照常追加在后面

### 15.3 什么时候获取

- **只获取今天的**：打开或回到「今日」时，今天没有天气记录、或者记录超过 3 小时，就重新获取一次并覆盖；过去的天永远不再改
- 获取失败（断网、超时）不报错，10 分钟内不重试
- **位置**：用系统缓存的最后一次位置，不管多旧——天气只需要城市级别；没有缓存才现场定位一次。坐标保留 2 位小数（约 1 公里）后才发出去
- **数据源**：Open-Meteo（免费、不需要 key），直接复用 agent 的 `android-weather` 背后的 `WeatherManager.fetchWeatherJson`，取每日预报的第 0 天（`timezone=auto`，就是当地的今天）
- **权限**：复用定位权限。没有权限时，第一次显示「今日」会请求一次（和碎碎念记录位置共用"只问一次"的标记）；拒绝就关闭天气并提示可以在「⋯」里重新打开。在「⋯」里手动打开天气时，如果没有权限会再请求

### 15.4 显示

- 分隔线文字：`今天 · 10月12日周一 · 🌦 小雨 18–23°`。没有天气记录的天只显示日期。始终一行，放不下时末尾省略
- 天气词按 WMO 代码归类：晴、晴间少云、多云、阴、雾、毛毛雨、冻雨、小雨、中雨、大雨、雪、阵雨、雷阵雨

### 15.5 备份

- front matter 跟着 day 文件导出
- 恢复时：本地没有、备份里有的 front matter key 补进来（所以换手机后过去的天气还在）；两边都有的保留本地

### 15.6 以后再考虑

- 每条碎碎念记录当时的天气
- 天气预警
- 和 companion 联动（下雨天撑伞）

## 16. 天气提醒（2026-10-12 新增）

未来两小时内会改变用户行动的天气——快下雨了、雷雨、大雨大雪、大风——以及当天的极端高温、低温和骤降，用系统通知提醒一次。

### 16.1 已定的规则

- **默认开启**，「⋯」菜单里「天气提醒」可以关
- **固定模板**，不用大模型：离线可用、及时、不花 token
- **每小时检查一次**，只在白天（7:00–22:00）发通知

### 16.2 触发条件

数据来自 `WeatherManager.fetchAlertJson`（Open-Meteo：当前降水和天气代码、未来几小时逐小时降水概率/雨量/天气代码/阵风、昨天和今天的最高最低温）。"未来两小时"包括正在进行的这个小时。

| 类型 | 条件 | 模板 |
|---|---|---|
| 雷阵雨 | 天气代码 95–99 | ⛈ 14:00 左右有雷阵雨，尽量待在室内，远离树下和高处 |
| 大雨/大雪 | 代码 65/67/75/82/86，或雨量 ≥4 mm/h | 🌧 14:00 前后有大雨或大雪，出行注意安全，能晚点出门就晚点 |
| 快下雨了 | 现在没在下，且某小时降水概率 ≥70%、雨量 ≥0.5 mm | 🌧 14:00 前后可能开始下雨，出门记得带伞 |
| 大风 | 阵风 ≥50 km/h | 🌬 14:00 前后阵风较大（约 62 km/h），注意高空坠物，收好阳台上的东西 |
| 高温 | 今天最高 ≥35° | 🥵 今天最高 36°，注意防暑，多喝水，中午少出门 |
| 低温 | 今天最低 ≤-5° | 🥶 今天最低 -6°，注意保暖，路面可能结冰 |
| 骤降 | 今天最高比昨天低 ≥8° | 🍂 今天比昨天降温 10°，记得添衣 |

- 降水类只取最严重的一种（雷阵雨 > 大雨大雪 > 下雨）
- 时间按**预报地点的当地时间**（接口返回的 `utc_offset_seconds`），白天时段按手机时间
- 没有官方气象预警：Open-Meteo 不提供，国内官方预警也没有免费公开接口。这里是"根据预报自己判断"
- **结合打卡**：今天还有没完成、名字像户外活动的打卡项（跑、步、骑、球、徒步、run、walk、bike……）时，降水/大风/高温提醒后面加一句「今天的「跑步」还没完成，可以改到室内，或者趁天气变化前完成」

### 16.3 位置

- **不申请后台定位**。「今日」在前台获取当天天气时，把粗略坐标（2 位小数，约 1 公里）存下来；每小时的检查用这个坐标
- 代价：换了城市后要打开一次 App 才会更新位置。还没获取过天气（没有坐标）就不检查

### 16.4 克制

- 降水类：4 小时内不重复，除非升级（下雨 → 雷阵雨）
- 大风：4 小时内不重复；高温、低温、骤降：每天一次
- 每天最多 3 条通知；22:00–7:00 不检查
- 单独的通知渠道「天气提醒」，可以在系统设置里单独关掉

### 16.5 App 里

当前有效的提醒固定在顶栏下面（不随时间线滚动），浅色底的一段，打开「今日」就能看到（2026-10-12 用户反馈：原先放在今天的日期分隔线下面，往回翻就看不到）。右侧 × 可以关掉：记住关掉的是哪几类提醒，同一类只是时间、风速变化不会再出现，出现新的类别（比如下雨升级成雷雨、又来了大风）才重新显示；没有提醒时一并清掉。只影响 App 里，不影响通知。存的是提醒数据（类型、时间、数值），显示时才按当前语言和今天的打卡状态生成文字，所以打完卡后「还没完成」那句会随之消失。有效期：逐小时类到事件开始后 2 小时，全天类到当天结束。检查发现没有提醒时清掉

### 16.6 调度和权限

- `AlarmManager.setInexactRepeating`，每小时一次（系统会合并唤醒，省电）。打开「今日」、打开开关时注册（幂等）；开机和 App 更新后由现有的 `offload/AlarmReceiver` 重新注册
- 接收器不对外导出，只有自己的闹钟能触发
- Android 13+ 需要通知权限：默认开启，所以第一次在「今日」里获取天气后请求一次（在定位权限之后，不会两个弹窗叠在一起）；拒绝了就只在 App 里显示。手动打开开关时会再请求

### 16.7 以后再考虑

- 官方气象预警（需要付费数据源）
- 让 Minis 写更贴心的提醒（需要模型，后台会花 token）
- 逐 15 分钟的降水（精确到"20 分钟后开始下雨"）

## 17. 认识身边的生命（2026-10-13 新增）

照片里拍到花草虫鸟时，「今日」在手机上认出它是什么，用户点一下就记下来，慢慢攒成自己的自然图鉴。识别**完全在手机上**完成，照片不上传。

### 17.1 模型和物种名单

- **模型**：BioCLIP 2（MIT，OSU Imageomics），只用图像编码器（ViT-L/14，3 亿参数）。照片 → 768 维向量，和物种名的向量比相似度
- **NPU 优先，CPU 要用户打开**（2026-10-13 用户决定只用 NPU；2026-10-14 改：CPU 方案也放出来，但要打开开关才用，尽量让大家用 NPU 版本）：静态量化版（权重 8 位、激活 16 位，QDQ 格式，305 MB），走 ONNX Runtime 的 QNN，跑在骁龙的 Hexagon NPU 上，每张约 30 ms（骁龙 8 至尊版实测）
  - **CPU 后备**：只有 NPU 用不了的手机（不是骁龙、Android 12 以下、或者 NPU 编译 / 运行失败过）才在「今日」⋯ 菜单里出现「用 CPU 认动植物」开关，默认关；打开前弹一句说明（结果一样，每张几秒钟、更耗电，只看画面中间，自动识别只看今天的照片），确认后才打开。NPU 能用的手机永远走 NPU，看不到这个开关
  - CPU 直接用同一个模型文件（ONNX Runtime 的 CPU，4 线程），不用多下载：Mac 上每次 713 ms（另一份动态 int8 模型 277 ms，但要多下 308 MB），内存约 0.5 GB。每张照片只看画面中间、左右翻转各一次（2 次；NPU 是最多 17 次），用户在「认一认」里拖框仍然可以认边上的东西。模拟器上实测每张 9–12 秒（模拟器的 CPU 比手机慢很多），5 张测试照认对 4 张（海象、君子兰、睡莲、蒲公英；鹈鹕相似度低、不提示），时间线上白头鹎、鹊鸲也认对了
  - CPU 不预加载（省 0.5 GB 内存），CPU 的失败不算 NPU 的失败次数；CPU 下的结论记了版本，以后换回 NPU 会重新看
  - 支持范围：Android 12+ 的骁龙手机，且只打包了 V73（8 Gen 2）及以后的驱动。更早的骁龙第一次编译会失败；联发科、Exynos、Tensor 的 NPU 走各自的接口，这一版不支持。不支持时所有识别入口都不出现
  - **只在第一次编译**：首次加载把模型编译给 NPU（约 35 秒），结果缓存在 `noBackupFilesDir/species-npu/<模型大小>-<修改时间>/`，之后每次打开都读缓存（约 0.4 秒）。只有换了模型文件、清除 App 数据、或缓存读不了（比如升级了 QNN）才重新编译；覆盖安装升级 App 不会
  - 编译失败，或者连续 3 次运行失败（每次失败都会丢掉缓存、下次重新编译）→ 这个 App 版本里关掉识别功能；App 升级后再试
  - 空闲 90 秒释放模型
- **物种名单**：iNaturalist 上在中国有 ≥3 条可验证观察的物种（约 3.7 万种），名字从 iNat 取中文名；和 BioCLIP 的名字对不上的，用 GBIF 的同物异名对齐；BioCLIP 官方向量表里缺失的（表的末尾 15,487 种向量全是 0，以及根本没收录的），用 BioCLIP 2 的文本编码器补算。向量存成每行一个缩放系数的 int8（约 21 MB）
- **家养的也在名单里**（2026-10-13 补）：iNaturalist 上中国「栽培 / 饲养」的观察（盆栽、园艺花卉、宠物、动物园），和野外的观察数相加后 ≥3 条的都收进来，新增约 2,800 种（竹节秋海棠、大王秋海棠、长寿花、郁金香……）；人（智人）除外。起因：一盆竹节秋海棠拍得再好也认不出，因为名单原来只有野外物种
- **属的中文名**（2026-10-13 补，用户反馈「看起来是 Begonia 的一种」对中文不友好）：一个属的中文名在名单里共享（同属任何一行有，全属都用）；iNat 没有的，从 Wikidata 按学名 + 属级精确查（补了 870 个）。有中文属名的物种从 79% 提到 97%。**名字以学名为准**：标签、图鉴、缓存的建议显示的名字一律按学名从当前名单取（物种的中文名，否则属的中文名），文件里随标签存的名字只在名单里没有时兜底——名单改进了，所有地方的名字一起变，不用逐处修补；实在没有中文的属，中文界面显示「Begonia 属的一种」
- **先找主体再认**（2026-10-13 补；同日用户反馈框得不稳，**ML Kit 已换掉**，改为识别模型自己在画面里找：中心 + 3×3 个 60% 的块 + 2×2 个 75% 的块，最有把握的一块比中心高 0.15 以上才用它，只有中心和胜出的那块做左右翻转。以下是最初 ML Kit 方案的记录）：照片以短边约 1024 像素解码，用 Google ML Kit 物体检测（模型打包在 App 里，约 2 MB，离线，不依赖 Google 服务）找出最显眼的至多 3 个东西（它很有把握是食物、衣物、家居用品的跳过，太小或几乎整张的框也跳过），每个框放大 15% 补成正方形，和画面正中的正方形各认一次；默认用正中的结果，某个框的把握（物种或属的概率，相似度够了才算）比正中高出 0.15 以上才换成它。在 Mac 上用 42 张测试照和 12 张生活照比过：直接取「最有把握的一块」会多出几个错答，加 0.15 的门槛后只改对不改错，生活照也没有新的误报
  - 起因：一张竖拍的照片里秋海棠只在左下角一小块，只看正中时大半是墙和衣柜，模型猜成了像叶子的螳螂（5%）
- **原图分辨率、左右各看一次**（2026-10-13 补）：每一块都从原图里只解码那一块（`BitmapRegionDecoder`，按 EXIF 方向换算、再转正），够 224 像素的两倍就停止放大采样——原先从短边 1024 的预览图里裁，一只占画面 3% 的小蜘蛛只剩三四十像素、放大后是一团糊；框只补成正方形，最小按原图的 224 像素，不再被放大到预览图的 224 像素（约画面的 22%）。每一块再左右翻转看一次，两个向量相加后归一化再比（Mac 上 42 张测试照：36 → 37 张认对，药用蒲公英从「暗色蛇纹春蜓」改对）
- **地点和季节先验**（2026-10-13 代码和数据都已就绪，数据由 `provinces.py` → `geo_months.py` → `build_prior.py` 生成，29 个省份可用、2.2 万种有月份数据；没有 `species_prior.bin` 时不加权）：`species_prior.bin`（可选，没有就不加权），iNaturalist 上每个物种在 34 个省级行政区有没有记录、全国每个月的观察数（和相邻月平滑后，按最旺的月折成 0–255；少于 10 条的不给季节）。识别时按照片的 GPS（没有就用「今日」上次定位的位置）反查省份、按拍摄月份，给打分乘上温和的权重：省里从没记录 ×0.4，淡季最低 ×0.5——只用来在长得像的几种里挑，不推翻明确的匹配。一个省都没有记录的（手工补的宠物等）当作哪里都有
- 限定在中国名单里，比在全部 87 万种里比准得多：全量时银杏会被认成化石种、鹊鸲会被认成马达加斯加鹊鸲
- 文件放在 `getExternalFilesDir("species")`：`bioclip2_img_w8a16.onnx(.data)`、`species.bin`、`species.tsv`。没有这些文件就不显示任何识别相关的东西。**第一版靠 adb 推送，正式版需要应用内下载**。托管（2026-10-14 用户决定）：GitHub Release 附件，`https://github.com/nazhenhuiyi/OpenMinis/releases/download/species-model-v1/<文件名>`——release 附件没有流量限制、单个文件 < 2 GB；没用 Git LFS，因为这个仓库是公开 fork，LFS 文件推不上去（推了也算在上游的额度上），而且免费 LFS 每月只有 10 GB 流量（约 30 次完整下载）。模型或名单更新时发新的 release（`species-model-v2`…），release 说明里有每个文件的 SHA-256

### 17.2 时间线上的提示

- 「今日」加载或刷新后（打开、回到前台、相册有新照片、日记有变化），在后台对**最近 3 天**（今天和前两天）的照片组逐个识别，新的在前，**每组每一张都看**；每张只看一次，结论按相对路径缓存（`today_species` prefs）；识别方式或名单变了（缓存版本号）就清掉模型的结论重新看，用户点过 × 或去掉过的（记为 `x`）保留。更早的照片不主动识别，用「认一认」（2026-10-13 用户决定：范围缩到 3 天、每组全部识别）
- **不会自动加入**（2026-10-13 改，用户：推荐出现时用户关心的是"这到底是什么"，加入要一个强动作按钮，否则容易误触）：自动识别只给建议，加入图鉴永远是用户在「这是什么？」页上点大按钮。原先把握 ≥90% 会直接贴标签，已去掉
- **只在很有把握时提示**：最可能的物种概率 ≥ 50%，并且照片和它的相似度 ≥ 0.70；常被当成食物、饮料拍的物种（咖啡、茶、稻、洋葱、番茄、苹果……）不主动提示——一杯拿铁在模型看来确实像小粒咖啡；否则看属——同属的几种加起来 ≥ 70% 时说「X 属的一种」。相似度门槛用来挡掉咖啡、饭菜、街景、天空这类照片（用文字描述做"非生物"类别没用：BioCLIP 2 的文字空间只认学名）
- 把握在 50%–90% 之间的，照片组下面出现浅绿色的提示（淡入）：左边是**被认出的那张照片的小缩略图**，中间「🐦 很像白头鹎」（概率 ≥ 80% 说「很像」，否则「看起来是」）和学名，右边是「看看 ›」和 ×。**一组里认出几种就有几条**；同一种的多张合成一条，学名后面写「· 3 张」。提示条上没有加入按钮：点它进「这是什么？」。以前认过的照片一次显示出来；新照片一组一组地认，**一组认完才一起出现**（时间线只刷新一次，不是每张一次）
  - **加入图鉴**（在「这是什么？」页上）：物种成为**这张照片的标签**，照片留在原来的组里（或原来那条碎碎念下面），不新建碎碎念（2026-10-13 用户反馈：最初的做法是生成一条新碎碎念，照片被拉出组，一组照片被拆成好几行）

- **记下的那一刻**（2026-10-13 用户：要有仪式感，每次加入都要有动画，动效要好，把之前那个团子加进来）：每次加入图鉴都发一张牌，在自己的全屏窗口里（盖住底部 tab 栏和系统栏，2026-10-14 用户反馈原先 tab 栏还露在外面），轻点任意处或返回键结束，「看看它」直接打开这个物种的页面

  - 右上角「选择」，或长按一张卡片，进入多选：卡片右上角出现勾选圈，顶栏「已选 3 种 · 全选 · 🗑」；返回键退出多选
  - 物种页右上角 ⋮：「移出这张照片」（只有多张照片时有，移的是当前看的那张）和「从图鉴删除」
  - 删之前都会问一句（「从图鉴删除「白头鹎」？照片上的标记会去掉，这些照片以后也不会再推荐。照片和日记都不会删除。」），删完底部「已从图鉴删除 1 种　撤销」
  - 删除只去掉标记：照片上的 `species` 标签从当天文件的 front matter 里删掉，这些照片记为用户说过不（`x`），不会再被推荐；带 `species` 的碎碎念保留文字，只去掉物种字段。撤销把标签、字段和推荐缓存原样写回。编号按剩下的重新排
- 空的时候：一片叶子和一句「拍到花草虫鸟，点『记下』就会收进来」
- **打开不等**：每天的记录按日记文件的大小和修改时间留在内存里，打开图鉴时只重读变过的那几天（谁改的都一样：今日、Obsidian、agent）；照片的查询结果也记住，相册有变化才重查。页面先显示上一次的列表，再换成最新的；时间线上的自动识别跑完后顺手把图鉴准备好

### 17.5 打包

- 依赖 `onnxruntime-android-qnn`（带 Java API 和 QNN 驱动）。语音检测库自带一份 1.20 的 `libonnxruntime.so`，构建时把 QNN 包里 1.29 的那份放进本模块的 jniLibs，让它在合并时胜出
- **语音检测要打补丁**（2026-10-13 发现：换成 1.29 后语音输入加载失败，`cannot locate symbol "OrtGetApiBase"`）：语音检测库链接时带了符号版本，要的是 `OrtGetApiBase@VERS_1.20.0`，1.29 只提供 `@@VERS_1.29.0`。C API 本身向后兼容，所以构建时（`patchVad`）把这个库对 `Ort*` 符号的版本要求清掉，让它绑定到 1.29。回归测试 `VadRuntimeTest`：一句真人语速的语音，要检测到一次开始、一次结束
- **关掉 ONNX Runtime 的遥测**：1.29 的 AAR 在清单里注册了一个 provider，每次启动 app 都加载 24 MB 的运行库，并启动微软的遥测客户端（会读设备 id、系统和设备信息、网络和电量状态）。识别承诺只有学名离开手机，所以清单里把它移除（`tools:node="remove"`），创建环境时也 `setTelemetry(false)`；顺带启动时不再加载运行库
- 正式版开了 R8：ONNX Runtime 的 JNI 按类名创建和读取 Java 对象，AAR 自带的混淆规则只保住了遥测类，所以 `proguard-rules.pro` 整包保留 `ai.onnxruntime.**`（和语音检测库同样的问题：只在正式版出现）
- 只保留 V73（8 Gen 2）及以后的 NPU 驱动；APK 增加约 55 MB（其中 `libQnnHtpPrepare.so` 压缩后 37 MB，用于在手机上编译模型）
- Android 12+ 要在清单里声明 `libcdsprpc.so`（`uses-native-library`，非必需），否则应用看不到 NPU 通信库，QNN 创建设备时报 `QNN_DEVICE_ERROR_INVALID_CONFIG`

### 17.6 以后再考虑

- 模型文件的应用内下载（从 `species-model-v1` release 下载、断点续传、按 SHA-256 校验），以及只在 Wi-Fi 下下载；国内访问 GitHub 下载慢时的镜像

- 用 BioCLIP 2 当老师蒸馏一个 20–40 MB 的小模型
- 图鉴页面做成卡片墙，点进去看所有照片；「第 n 种」的徽章

## 18. 视频和碎碎念配图（2026-10-14 新增）

### 18.1 视频进时间线

- 相机拍的视频和照片一样出现在时间线上：同样的路径规则（§5.1）、同样的聚合规则（§5.2），和同一时段的照片聚在同一组里
- 缩略图取系统相册自己的视频缩略图（`loadThumbnail`，Android 10 以下取第一帧），右下角显示「▶ 0:23」
- 点开在同一个全屏查看器里，先显示封面和 ▶，点了才在原位播放；点画面暂停/继续，下面的进度条可以拖动；滑到别的照片就停止
- 视频**不做识别**：不参与物种建议和「认一认」；「问问 Minis」只带图片
- 视频也读地名：从文件里的位置标签（ISO 6709，比如 `+31.2304+121.4737/`）取坐标，和照片一样需要 `ACCESS_MEDIA_LOCATION` 并打开原文件；照片组的地名取组内第一个有位置的照片或视频
- 权限：`READ_MEDIA_VIDEO`（API 33+）和图片一起申请。以前只授权了照片的用户，打开「今日」时补问一次（和图片在同一个权限组，通常不弹窗）；拒绝了就不再问，只显示照片

### 18.2 碎碎念配图

相机拍的照片本来就会自动出现在时间线上，所以"配图"分成三种情况：

| 情况 | 入口 | 碎碎念记在什么时间 |
|---|---|---|
| 刚拍的 | 输入框 📷（§2.3，不变） | 现在 |
| 时间线上没有的图（下载的、截图、微信存图），或者别的照片和视频 | 输入框里的相册按钮：系统照片选择器，一次最多 9 项，图片和视频都可以 | 现在 |
| 给时间线上已有的一组照片写几句 | 长按照片组 →「写点什么」 | 这组照片的时间；地点用这组照片的地名，不重新定位 |

- **引用原图，不复制**：选择器给的是它自己的 URI，Minis 按"文件名 + 大小"，不行再按"大小 + 逐字节比较"找到相册里的原文件，`photos=` 存原图的相对路径（比如 `Download/xxx.jpg`）。只有找不到原图时（没有相册权限，或者只授权了部分照片）才复制一份到 `DCIM/Minis/`
- **只有图也能发**：选来的图不写字也会生成一条只有图的碎碎念，否则它们不会出现在时间线上。只有刚拍的照片、没写字时，才保持 §2.3 的规则（回到普通照片组）
- **× 只移出输入框**：选来的图点 × 不会从相册删除；只有刚拍的才会连同相册里的文件一起删（§2.3）
- **「写点什么」**：输入框上方显示「写给 09:32 的照片 ×」，那组照片作为待发送；必须写字才能发。点 × 回到普通碎碎念，并移除那组照片
- **自动时间线不变**（用户 2026-10-14 定的）：挂在碎碎念下面的照片，只有两种情况会从原来的照片组里移走——是 Minis 自己的文件（`DCIM/Minis/`），或者拍摄时间和碎碎念相差不到 3 小时。更早的照片两边都显示：原来那天的照片组里一份，碎碎念下面一份
- **编辑时增删配图**：编辑碎碎念时下面列出它的照片，每张有 ×，最后一格「+」打开选择器。去掉的照片只是不再挂在这条下面，相册里的文件不动（如果是相机拍的，它会回到自动的照片组）。文字和照片不能同时为空

## 19. 心情颜色和智能建议（2026-10-15，第一版已实现）

两个功能都建立在本地小模型给碎碎念打的标签上（`docs/design/today/MURMUR_MODEL.md`，Qwen3-0.6B 微调，Q4_0，手机上约 370ms/条、744MB）。作者 2026-10-15 要求先做一版。

### 19.1 打标签（两个功能共用）

- 碎碎念发送或编辑后，**停顿 30 秒**再打标签（刚发出去常常马上改）。在后台跑，用完就释放模型
- 输出：意图（记录/待办/查询）、情绪、方面、提及、高光
- 标签是**派生数据**，存在 `noBackupFilesDir/murmur/tags.json`（`MurmurIndex`），键是条目 id，带正文哈希和模型版本。正文变了、模型换了都会重打。没用 Room：不想为可丢弃的数据加数据库迁移
- 旧碎碎念：第一次打开功能后，在充电、空闲时慢慢补打
- 模型文件约 380MB，放在 `getExternalFilesDir("murmur")/murmur-0.6b-q4_0.gguf`。预览版用 adb 推上去；以后和物种模型一样从 GitHub Release 下载。文件不在时两个功能都不显示，「今日」照常使用
- 旧碎碎念：时间线上能看到的那几天随时间线一起打；更早的在打开心情月历时补打当月的（充电时全量补打以后再做）

### 19.2 心情颜色

**看到什么**

- **日期分隔线上一个小圆点**：`── 今天 · 10月15日 ● ──`，颜色是这一天的心情。只有当天有碎碎念时才显示
- **心情月历**：入口在「⋯」→「心情」，以及点日期分隔线上的圆点。一个月一页，每天一个浅色方块，没写碎碎念的日子留白。点某一天，跳到时间线上的那一天

```
┌─────────────────────────────┐
│ ←  心情             2026年10月 │
│ 一  二  三  四  五  六  日     │
│        ■  ■  □  ■  ■  ■     │
│ ■  ■  ■  □  ■  ■  □         │
│ …                            │
│ ■ 明亮  ■ 平常  ■ 低沉         │
└─────────────────────────────┘
```

**颜色怎么来**

- 每条碎碎念的情绪归成三档：积极（开心、满足、感动、期待）、平常（平静、好奇）、低沉（疲惫、低落、焦虑、烦躁、生气、难受）
- 一天的颜色按条数投票；积极和低沉的票数差不多时显示平常色，不硬判
- **颜色要柔和**：明亮用暖杏色，平常用浅灰，低沉用雾蓝。**不用红色**，红色像警报
- 模型三档准确率约 72%，正负判反约 2%。按天聚合以后会更稳

**克制**

- 不写评价，不出"这周心情不好""要注意休息"这类话
- 不推送、不提醒，也不拿心情做连续打卡
- 单条碎碎念上**不显示**情绪，只在日期和月历这一层显示，不给每句话贴情绪标签

**用户可以改**

- 在月历里点开某一天，每条碎碎念旁边有一个小色点，点一下在三档之间切换
- 用户改过的情绪写进 journal 条目的元数据（`mood=明亮`）。这是用户自己的数据，要进备份，重打标签时也不能覆盖

**开关**：「⋯」→「心情颜色」，默认打开（全部在本地完成）。关掉以后圆点和月历入口都隐藏，已有的标签不删

### 19.2a 时间线里的心情（2026-10-15 改版，替代上面的圆点）

作者反馈：圆点不好发现、看不出每条的心情，月历方块太重、深色模式下扎眼。改成：

- **每条碎碎念**：时间那行小字后面一个 15dp 的线条图标，染成所属一档的颜色，"平静"不显示。开心 ☺、满足、感动 ♡、期待 ✦、好奇（指南针）、疲惫（月亮）、低落、焦虑、烦躁、生气（火苗）、难受（创可贴）。点图标在下面原地展开选择器
- **选择器**：12 个词按明亮 / 平常 / 低沉分三行，每个是"图标 + 词"的浅色小块；选中的填深。用户选的写进条目的 `mood=`（具体的词，旧版写的三档名也认）
- **每一天**：不再有圆点；日期分隔线两侧的横线染上当天的颜色（很淡），点日期文字打开月历
- **配色**：半透明的墨色（鼠尾草绿 `#84A98C`，作者 2026-10-15 从杏色换的；灰 `#959BA4`、雾蓝 `#7896BA`），浅色和深色页面通用
- **月历**：无边框，有心情的日子是柔和的圆形色块，其余只是浅色数字；当天碎碎念前是"图标 + 词"的小标签，点开改
- **建议卡片**：和物种建议同一个样子（柔和底色、淡入、粗体第一行、彩色动作、淡 ×）

### 19.2b 没把握就不上色（2026-10-16）

借鉴 Jev（TypeSafe AI 的 System One 模型）的思路：每个判断都带一个校准过的概率，没把握的就不显示。

- 模型生成到心情这一项时，读出 12 种心情各自的概率（从原始 logits 读，在语法约束之前），合并成明亮、平常、低沉三档，再用温度 T=2.4 校准，得到所选那一档的把握度，存进标签（`mc`）。
- 读不到概率时（心情这一项正好从一个词元中间开始），把握度记为 0：不显示，也不会反复重跑。
- 模型给的心情，把握度 ≥ 0.7 才在时间线和心情月历上显示（起初是 0.8，上色太少，2026-10-16 作者定为 0.7：约 62% 上色，其中 85% 对）；没把握的保持不上色，但仍然可以手动选。用户自己选的心情总是显示。
- 依据（`scripts/murmur_train/system_one.py`，在 244 条真实碎碎念上测）：
  - 心情分档整体准确率 75%，但模型过于自信。
  - 校准后误差 ECE 从 0.15 降到 0.05。
  - 门槛设为 0.8 时，约 43% 的碎碎念会上色，其中 88% 是对的。
  - 同一实验里，改成逐题提问（判断题）的方式：微调模型心情准确率只有 19%，原版 Qwen3-0.6B 也只有 32%，而且更慢，所以不采用。
- 之前打的标签没有把握度：只在心情颜色开着时，才顺带重打时间线上的那几条；打开心情月历时补打这个月的。其余的（菜单、探索要用的标签）不受影响。

### 19.3 智能建议：粗筛之后直接交给 Minis（2026-10-16 改版）

**流程**

```
写碎碎念 → 本地打标签 → 本地粗筛通过？ → 后台开一个 Minis 对话（不出现在聊天列表）
                              ↓ 否                     ↓ Minis 回「不需要」
                            到此为止              删掉这个对话，什么都不显示
                                                       ↓ 有可做的
                              碎碎念下面一行：💬 Minis 写的第一句 · 继续聊 › · ×
                                                       ↓ 点开
                              对话进入聊天列表，接着聊（设提醒、深入查……都在对话里做）
```

- **本地粗筛要召回率**：满足任意一条就送去云端：
  - 模型认为可能要办，P(非记录) ≥ 0.02；
  - 命中关键词：明天、记得、准备、怎么、什么……呢，以及办事词注销、取消、退订、续费、到期、预约、挂号、截止；
  - 心情是「好奇」，往往是没问出口的问题（2026-10-16 加入）；
  - 写了想做的事：和心愿单（§20.1）用同一套规则 `MurmurLabels.WISH`，即"想、好想、很想、打算、有机会……"加上"看、读、去、买、学……"（2026-10-16 加入；起初只认"想看/想读/想去/想买/想学/想试/想吃"，后来和心愿单统一，范围略宽）。

  按作者的 244 条真实碎碎念（2026-10-16 在 Mac 上用同一个 Q4_0 模型测），22% 被送出，21 条待办或查询里抓到 20 条。好奇和心愿这两类在标注里算"记录"，所以不提高这个找回率；加进来是为了给答案或"问问 Minis"，每天最多 3 条建议的上限不变。
  - 好奇和心愿起因：作者写了一条对国际局势走向的好奇，按当时的单次云端提示词得到 none；现在由 Minis 自己判断，规则里明确包括没问出口的好奇和想做的事。
  - 试过但没加：提到症状或药（多送 7 条，多是"有点累"之类随口一说，回应容易显得多管闲事），"要不要、该不该"（作者数据里没有）
- **Minis 在后台准备**（`data/murmur/MurmurAgent.kt`）：
  - **怎么跑：** 用和定时任务同一套后台对话机制（`HeadlessChatRunner`），新建一个对话，来源标成 `murmur_pending`。聊天列表、移动到对话、搜索、启动时跳到最近对话都看不到它，完成时也不发通知。
  - **第一条消息：** 用户口吻，点开后能看到：「我在「今日」写了一条碎碎念（时间）：> 原文 …… 帮我看看有没有我用得上的。」
  - **这一轮的规则：** 只在这一轮附在系统提示词末尾（`ChatViewModel.murmurBrief`），跑完就去掉：
    - 用户不在场；先判断有没有值得帮的：要做的事（提出提醒）、想知道的事、没问出口的好奇、想做的事。感慨、已经做完的事不用管；
    - 不需要就只回「不需要」；
    - 需要的话，第一行写一句不超过 30 字、单独看也能懂的总结，空一行再写正文；
    - 可以用 shell 查资料，但只准备、不动手：不设提醒或日程、不发消息、不写文件或记忆，需要动手的写成建议，等用户回复。
  - **工具：** 这一轮去掉会自己动手的工具：`memory_write`、`browser_use`、日记工具、子 agent。保留 `memory_get` 和 shell，用来查资料。shell 本身什么都能做，所以"不动手"有一部分只能靠上面的规则约束，这一点在开启说明里如实写了。
  - **结果：**
    - 回复「不需要」：对话删掉，记下 none；
    - 有可做的：记下第一行和对话 id；
    - 失败或超时（4 分钟）：对话删掉，什么都不记，下次再试。
  - **版本号：** `BRIEF_VERSION` = 3（1、2 是之前的单次云端判断）。旧版本判断过、用户没动过的（none 或没处理的建议），24 小时内会用新流程再跑一次。
  - **排队：** 由 app 级别的 `MurmurAgentQueue` 负责，生命周期和 app 一样，跟定时任务一样：「今日」只把通过粗筛的碎碎念交过去，再观察"正在看哪条"和结果；「今日」页的 ViewModel 被销毁时，正在准备的那条不会中断、对话也不会被删掉。一次只跑一条；清理和准备走同一条队列，不会互相打架。不耽误给新碎碎念打标签。
- **只发文字**：这条碎碎念的文字和时间；Minis 自己会带上它的系统提示和记忆，不发位置和照片
- **花费**：按作者的写作量，每天大约 2 条碎碎念，22% 送出，平均两三天一次，花费可以忽略

**看到什么**：碎碎念下面一张浅色小卡片，淡入出现：

```
09:32
止痛药还是牛，感谢布洛芬……感觉晚上睡觉前得吃一颗
   💬 今晚 22:30 提醒你吃布洛芬？          继续聊 ›   ×
      Minis 帮你看过了
```

- **卡片：** 第一行是 Minis 写的摘要，第二行是正文的开头（最多一行），扫一眼就能决定要不要点开。
- **动效：** 只有"这次运行里刚生成、还没看过"的卡片才淡入一次，这个标记由数据层给出（`MurmurAgentQueue.fresh`），淡入完就清掉；之后滚动、切 tab、刷新都直接显示，不重播（2026-10-16 作者：每次出现都动，碍眼）。自然图鉴的识别卡片也一样：只有刚识别出来的才淡入。两者共用 `AppearOnce`。
- **正在准备：** Minis 在后台看某条碎碎念时，那条下面有一行很淡的「Minis 正在看这条…」，不加动画；准备好了换成卡片，判断不需要就什么都不留。后台跑的时候通知栏会有 Minis 的常驻通知，这是系统要求的前台服务，防止锁屏后任务被杀，跑完就消失。
- **清理：**
  - 重做或者碎碎念改过时，先删掉以前那次的后台对话；已经点开过的对话属于用户，不删。
  - 每天最多清理一次：点过 × 的、或者超过 7 天（`MurmurAgent.KEEP_DAYS`）还没点开的对话删掉；关掉智能建议时，没点开的全部删掉，同样只做一次。
  - 兜底：app 冷启动时，删掉 8 天没动过、也没点开的碎碎念对话（`MurmurAgent.sweep`，按数据库查，不依赖「今日」的记录），覆盖跑到一半被杀掉、或者很久没打开「今日」的情况。
  - 隐藏范围：聊天列表、移动到对话、定时任务的目标对话、搜索、启动时跳到最近对话、Minis 自己查对话列表时，都不显示没点开的碎碎念对话。规则只写在一处：`ChatSessionEntity.isHiddenFromLists`，以及它的 SQL 写法 `SHOWN_IN_LISTS`（两者写在一起）。没有改成数据库字段：仓库是上游的分支，加数据库版本会和上游以后的迁移撞车。
- **模型：** 和定时任务选模型的方式一样：默认分组里第一个有凭证的成员（同时写入分组绑定），否则第一个有凭证的模型；记忆开关跟随全局设置。
- **点卡片：** 对话的来源改成 `murmur`，出现在聊天列表里，切到聊天并打开它，接着聊。在对话里回"好"，Minis 才去设提醒。卡片的小字变成「已在聊天里」，× 消失。
- **点 ×：** 这条不再显示，可以撤销。对话等第二天清理时一起删。
- **显示规则：** 时间线上只显示当天的，最多 3 条。
- **智能建议页**（2026-10-16 作者：多了不好管理）：从探索页的「智能建议」进入，列出最近 7 天 Minis 准备好的全部对话，按天分组，每条是碎碎念原文加同样的卡片，可以点开接着聊或点 × 收起（可撤销）。Minis 正在看某条时顶上有一行提示；没开智能建议时提示去设置里打开。
- **没有可用的模型时：** 开关灰掉，小字「先在设置里配一个模型」。

**以前的做法（2026-10-15 ～ 16，已删）：** 一次云端调用返回 JSON，分提醒、答案、问问 Minis、不需要四种；本地负责定时提醒（`MurmurReminder`）、改时间、展开答案。作者觉得太绕，改成现在这样：粗筛后直接让 Minis 处理，点开就接着聊。

### 19.3a 交互打磨（2026-10-15；提醒、回答、时间相关的几条已随 19.3 改版作废）

- **一行**：建议是一行浅底小条：图标、文字、最多两个小动作。「不用」是 ×；提醒是「提醒我」，回答是「继续问」，交给 Minis 是「问问 Minis」
- **时间能改**：提醒里的时间用强调色，点一下在原地展开时间输入（和打卡提醒一样，没有弹框）。保持原来那天；改成今天已过的时间就顺延到明天
- **都能撤销**：「提醒我」「×」「取消」之后，底部出现「会在今天 22:30 提醒你 撤销」「这条建议不再显示 撤销」「已取消提醒 撤销」。闹钟永远跟着存下来的状态走，撤销就恢复原样
- **提醒响过以后**：变成「已提醒 · 22:30 · 吃布洛芬」，没有按钮；那天过完就不再显示
- **回答**：先显示两行，点文字展开全文，不再有单独的「展开」按钮
- **通知**：标题是要提醒的事，正文是那条碎碎念原文
- **没有可用的模型**：「智能建议」灰掉，下面一行小字「先在设置里配一个模型」
- **第一次出现颜色**：底部一次性提示「日期旁的小圆点是这一天的心情 看看」，点「看看」打开月历；以后不再出现
- **改颜色**：点碎碎念前的圆点，在下面展开「明亮 / 平常 / 低沉」三个带名字的色块，点哪个就是哪个（原来连点切换，不知道下一下会变成什么）
- **更快**：发完停 2 秒就打标签（原来 30 秒，后来 15 秒；2026-10-16 作者觉得 15 秒太久）。代价是写完马上又改的话，第一版也会被读一次；开着智能建议时，第一版可能已经交给 Minis 在准备，改完会删掉那次的对话、按新内容重来

## 20. 探索（2026-10-15，第一版已实现）

第三个 tab。目的是给人惊喜：把你自己日子里的东西，用你没想到的方式递回给你。所有内容都来自手机上的日记，不联网。页面内容有限，不是刷不完的信息流。

### 20.1 页面

从上到下：

1. **今天翻到的一页**。每天最多 3 页，同一天里每次打开都是同样几页，第二天换新的。翻到第几页会记下来，最后一页的按钮显示「明天再来翻」；点圆点可以回到前面的页。
   - 先放"N 个月 / 年前的今天"：往回看 48、36、24、12、6、3、2、1 个月的同一天，取那天最值得看的一条（有照片的优先，其次字多的）。如果那个月没有这一天（比如 31 号），就跳过。
   - 交互：
     - 左右滑动卡片就能翻页，翻的时候按方向滑入，并有一下轻微震动。
     - 当前页的圆点会拉长；圆点的点击范围比看上去大。
     - 照片超过 3 张时，第 3 张上显示"+N"。
     - 点卡片打开**那一天**：那天的全部碎碎念，文字完整显示，照片全部列出，翻到的那条用一道金色竖线标出来，打开时直接滚到它。
   - 剩下的位置随手翻：从 14 天以前的碎碎念里随机抽，随机种子是当天日期。有照片的权重 +2，字数 ≥40 的权重 +1。太短又没有照片的不选。如果没有 14 天以前的，就从今天以前的里面抽。
2. **两个入口**：「自然图鉴」和「吃喝」（也就是我的菜单 §19.6）。有照片时用最近一张当封面。「吃喝」要等碎碎念模型准备好，或者已经有吃喝相关的碎碎念才会出现。这两项从今日页的 ⋯ 菜单搬到了这里；时间线上的物种标签仍然直接打开图鉴。
   - 下面是「心情」和「智能建议」（碎碎念模型在手机上时才有）。「心情」是一张横卡，直接露出最近 7 天每天的心情 emoji（没有的那天是一个淡点），点开是心情日历（§19.2，2026-10-16 从今日的 ⋯ 菜单搬来，时间线日期分隔线上的心情仍然可以点开）；「智能建议」打开智能建议页（§19.3），小字显示「今天 N 条」「最近 7 天」或「未开启」。心情页不再要求开着「心情颜色」：打开时总会补上还没有把握度的标签。
3. **心愿单**（2026-10-16）：碎碎念里写到想做的事，比如"好想去莫高窟""很想学做手冲咖啡""有机会试试"。
   - **识别：** 规则匹配"想、好想、很想、打算、有机会"加上"看、读、去、买、学、试、吃、玩、做、写、画、养、种、拍、听"。所在句子里有"什么"的不算，多是感慨，比如"想做点什么才好呢"；有"于是、结果"的也不算，多是已经做了，比如"想喝粥，于是煮了一锅"。在作者的 331 条碎碎念里找到 6 条，都是真心愿。
   - **探索页上：** 显示还没做到的最新 3 条和"全部 ›"。点前面的圆圈就算做到了：圆圈先填满打勾，再从列表里消失，同时震一下，弹出"做到了 🎉"，可以撤销。点句子打开那一天。
   - **心愿单页：** 每条都有"帮我查查"，用这句话开一个新的 Minis 对话草稿；还有"不想了"，同样可以撤销。下面是"做到了的"，显示做到的日期，点圆圈可以放回去。
   - **存储：** 做到了、不想了是作者自己的判断，所以和手动选的心情一样写进日记那一条：`wish=done|dropped`，做到的日期写在 `wish_on=yyyy-MM-dd`。
4. **第一次**：并排最多 3 张小卡片，不再横向滑动（2026-10-16 作者：克制一点），每张是当时的照片、名字和日期。物种和菜各取最近 2 个，合在一起按时间从新到旧取 3 个，这样植物多的月份不会把菜挤掉。点物种直接打开图鉴里的那一种，返回时直接回到探索，不经过图鉴列表。从时间线上的物种标签进去也一样。点菜会打开我的菜单，滚到第一次写到这道菜的那条碎碎念，那条的背景先亮一下暖色、再慢慢褪掉，菜名标签也跟着加深。我的菜单里的照片可以点开看大图，超过 3 张时显示"+N"。
5. **小发现**：每天只露出 2 条（按日期换一组，2026-10-16 作者：不需要露出这么多），候选是：一共几条碎碎念（从哪天开始）、写了多少字、最长连续记录几天、最常在一天中什么时候写（清晨 5–8 / 上午 8–12 / 午后 12–17 / 傍晚 17–20 / 夜里）、最满的一天、照片数。

卡片按下时会轻轻缩小一点。在探索页按返回键，先回到今日。

不做排行、不提示"断签"，也不和别人比。

### 20.2 实现

- Tab：`MainTabs.Tab.EXPLORE`，和今日一样是盖在 NavHost 上面的一层（见 MainTabs）。同一时间只组合正在显示的 tab，但 AppNavigation 用 `rememberSaveableStateHolder` 给每个 tab 保存状态，所以切回来时滚动位置还在。今日只有在离开期间有新内容时才会滚到最新一条。
- 状态：`ui/today/ExploreViewModel.kt`，独立的 ViewModel，Activity 存在期间一直保留。
  - 物种图鉴和吃喝碎碎念通过 `ExploreSources` 接口从 `TodayViewModel` 读取，这样可以复用今日已经建好的缓存。
  - 整页数据（`ExploreData`）在后台一次算好再交给界面：日记只读一遍，图鉴同时计算。
  - **何时重算**：只在探索显示在屏幕上时计算。打开时，以及日记、照片、碎碎念标签（`MurmurIndex.tagChanges`，只在真正写入标签时增加）有变化或换了一天时，重算一次；短时间内的多次变化等 0.6 秒合并成一次。不在屏幕上时的变化先记着，下次打开时如有变化补算一次。在手机上算一次 70～90 毫秒。
  - **启动时不算**：第一次打开探索时才开始算，这期间显示页面轮廓，算好后整页一起淡入。
  - 翻到第几页也由它管理：存在 prefs `today_explore`（日期、页码）里，换了一天就回到第一页。
- 规则：`ui/today/Explore.kt`（`pages` / `facts` / `firsts`），测试在 `ExploreTest`。
- 界面：`ui/today/ExploreUi.kt`。我的菜单打开时，先显示探索已经算好的吃喝列表。返回键由 ExploreScreen 自己处理（先回到今日）。全屏子页面（心情、我的菜单、那一天）共用 `TodayPages.kt` 里的 `FullScreenPage`，三张一排的照片共用 `PhotoStrip`。
